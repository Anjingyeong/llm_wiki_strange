# 뷰스컴퍼니 LLM 사내 자동화 개발자 면접 완전 대비

> 목표: 회사와 JD를 외우는 자료가 아니라, **왜 이 회사가 LLM 자동화 개발자를 뽑는지 추론하고 내 프로젝트 경험을 실제 업무 문제 해결 방식으로 연결해 말하기 위한 실전 면접 노트**다.

## 0. 실전 면접 코스 — 평소에는 이것만 반복한다

이 페이지 전체를 외우는 게 목표가 아니다. **아래 28문항을 위에서 아래로 말해보면 1회 면접 준비가 끝나도록 만든 본편**이다.

기본 캐릭터는 하나만 유지한다.

> **“AI를 써서 필요한 기능을 빠르게 만들되, 실제 사용·로그·테스트를 보고 계속 고치는 주니어 자동화 개발자.”**

LLM 연구자처럼 보이려고 어려운 말을 늘리지 않는다. 반대로 “AI가 다 해줬다”로 끝내지도 않는다. **무엇을 만들지, 어디까지 자동화할지, 어떤 결과를 완료로 볼지는 내가 판단했다**는 선을 지킨다.

7. 다른 지원자보다 본인을 뽑아야 하는 이유는 무엇인가요?

11. 팀장으로 일하면서 가장 어려웠던 점은 무엇이었나요?
12. 새로운 기술을 빠르게 배워 적용했던 경험을 말해주세요.
13. 본인이 잘 모르는 업무를 맡게 되면 어떻게 시작하나요?

28. 마지막으로 하고 싶은 말과 회사에 묻고 싶은 질문이 있나요?

### 0-2. 답변은 문장보다 이 구조만 기억한다

모든 질문에 별도 모범답안을 외우지 않는다. 아래 중 하나만 골라 말한다.

- **경험 질문:** 상황 → 내가 한 판단 → 행동 → 결과 → 배운 점
- **업무형 질문:** 먼저 확인할 것 → 작은 해결책 → 검증 → 안정화/운영
- **기술 질문:** 왜 필요했는지 → 내가 선택한 구조 → 실제 결과 → 한계
- **인성 질문:** 내 성향 → 실제 경험 → 지금 어떻게 보완/활용하는지

첫 답은 **20~40초** 정도로 끝낸다. 더 물어보면 그때 세부 기술이나 숫자를 말한다.

### 0-5. 주니어답게 말하는 규칙

- “제가 다 설계하고 직접 구현했습니다”처럼 **코드 기여를 부풀리지 않는다.** AI가 많이 작성했다면 그대로 말하고, 대신 내가 정한 요구사항·구조·완료 기준을 설명한다.
- 모르는 세부 구현은 추측하지 않는다. **“그 부분은 AI 도움을 받아 구현해서 코드 기준으로 다시 확인해야 합니다”**라고 선을 긋는다.
- 회사 내부 프로세스는 아는 척하지 않는다. **“실제 현업 흐름과 데이터를 먼저 보고 판단하겠습니다”**가 정상적인 답이다.
- LLM이 필요 없는 문제에는 LLM을 붙이지 않는다. Python 스크립트, API, SaaS가 더 단순하면 그쪽을 제안한다.
- “여러 AI를 병렬로 돌리면 빨라집니다”보다 **검증과 유지보수까지 감당 가능한 범위로 일한다**고 말한다.
- 자동화의 목표를 사람 제거로 잡지 않는다. **반복 시간을 줄이고 사람이 중요한 판단에 집중하게 하는 것**으로 설명한다.
- 답하다 막히면 외운 문장을 찾지 말고 **“그래서 실제로 제가 해본 건…”**으로 위 6개 경험 중 하나에 돌아온다.

### 0-6. 상세 문서는 이렇게만 찾아본다

- 회사/JD가 궁금할 때 → **1~3장**
- 실제 업무 자동화 케이스를 연습할 때 → **3장 이후 업무 시나리오**
- JK·LLM Wiki·관제 기술 꼬리질문이 막힐 때 → **프로젝트별 질문/30초 카드**
- 인성 답변을 다시 잡을 때 → **16장 HR·인성 면접**
- 마지막 역질문을 고를 때 → **13장 역질문 TOP 12**

평소 복습은 **0장만** 한다. 상세 파트는 모의면접에서 실제로 막힌 질문만 내려가서 확인한다.

## 먼저 결론

2026-08-25 ULW research에서 잡코리아 원본 이미지/API를 복원해 상세 JD를 확인했다. 따라서 이 포지션의 핵심은 더 이상 추론이 아니라, **LLM 프롬프트를 설계·관리하고, 여러 단계를 워크플로로 오케스트레이션하며, 출력 품질을 eval로 검증하고, 부서 반복 업무를 코드와 AI로 자동화하는 실무 개발자**라고 볼 수 있다.

확인된 주요 업무는 **사내 LLM 프롬프트 설계·관리·개선, LLM 워크플로 오케스트레이션, LLM 출력 평가·검증 체계 구축, 텍스트 정제·분류·구조화, 부서 반복업무 자동화**다. 우대 기술에도 **RAG, eval, Claude/GPT API, 로컬 LLM, Python/JavaScript, Slack·Notion·Google Workspace 연동**이 명시돼 있다. 즉 면접 준비의 중심은 모델 연구보다 **업무 분석 → 데이터/텍스트 처리 → LLM → 검증 → 외부 도구 연동 → 운영**의 전체 흐름에 둔다.

### 2026-08-25 근거 조사 업데이트

이번 보강은 8인 전문 연구팀의 1·2차 조사 레인 결과를 기준으로 한다.

- 출처 **32개**
- 관찰 **21개**
- 주장 **19개**
- 주장 상태: **지원 13 / 부분지원 3 / 미해결 2 / 반박 1**
- 동명이인 자료 제거, 인용 누락 0, 지원자 경력·성과 임의 생성 0, 원장 무결성 검사 PASS

문서에서는 다음 원칙을 지킨다.

1. **확인된 사실**: 실제 면접 답변의 전제로 사용 가능
2. **회사 맥락 기반 추론**: 아이디어/케이스 면접에서만 가정임을 밝히고 사용
3. **부분지원·미해결·반박 주장**: 사실처럼 외우거나 지원동기에 사용하지 않음

그리고 뷰스컴퍼니 채용팀이 공개한 면접 분석에서 가장 중요한 힌트는 두 가지다.

1. **스스로 고민하고 선택해 본 사람**을 높게 평가한다.
2. 면접용으로 꾸며낸 답보다 **솔직한 선택 이유와 근거**를 높게 평가한다.

대표 역시 채용 메시지에서 경력 그 자체보다 **빠른 실행, 살아남은 경험, 끝까지 책임지는 태도**를 강조했다.

따라서 이 면접의 기본 답변 형식은 두 층으로 가져간다.

기술 경험을 깊게 설명할 때는:

**문제 → 내가 직접 고민한 선택지 → 선택 기준 → 구현 → 실패/한계 → 검증 결과 → 다시 한다면 무엇을 바꿀지**

지원동기·자기소개·“왜 당신을 뽑아야 하나요?”처럼 짧게 임팩트를 줘야 할 때는:

**① 내 필살기(증거) → ② 이 회사의 문제 → ③ 내 경험과의 연결 → ④ 문제 해결 캐릭터 한 줄**

이 두 번째 구조의 핵심은 “저는 무엇을 잘합니다”가 아니라 **그 강점이 왜 하필 이 회사의 현재 문제에 필요한지**까지 닫는 것이다.

- **텍스트 정제·분류·구조화**
- **각 부서 반복 업무를 코드와 AI로 자동화**

### 우대/연관 기술 — 확인된 사실

- RAG 및 LLM eval 경험
- Claude/GPT 계열 API 활용
- 로컬 LLM 활용
- Python / JavaScript
- Slack / Notion / Google Workspace 연동

### 이 JD를 한 문장으로 해석하면

**“프롬프트만 잘 쓰는 사람이 아니라, 현업의 반복 업무를 찾아 LLM과 코드를 워크플로로 묶고 그 결과를 평가·검증해 실제 사내 도구로 운영하는 사람”**에 가깝다.

### 해석

“바이브 코딩”을 제목에 직접 넣었고 실제 JD가 프롬프트·오케스트레이션·eval·반복업무 자동화를 함께 요구한다. 따라서 **빠른 프로토타이핑 능력 + 운영 가능한 워크플로 설계 + 검증 체계**를 한 묶음으로 보여주는 것이 중요하다.

특히 JK는 실행/권한/상태/실패 복구, LLM Wiki는 RAG/eval/근거 관리 경험을 설명할 수 있어 이번에 복원한 JD와 직접 맞닿는다.

# 2. 회사가 지금 어떤 문제를 풀고 있는가

## 2-1. 광고대행사에서 콘텐츠/IP/커머스 구조로 이동 중

뷰스컴퍼니는 뷰티 콘텐츠 중심 마케팅 대행사로 시작했지만, 최근 대표 메시지에서는 단순 광고 대행을 넘어 **크리에이터 IP → 콘텐츠 → 팬덤 → 브랜드 → 커머스/글로벌 유통**을 연결하는 구조를 강조한다.

대표 공개 자료 기준으로 2024년 매출은 136억 원, 신규 MCN 브랜드 비라운드는 첫해 56억 원 실적을 기록했다고 밝혔다. 2025년 상반기에는 매출 92.4억 원, 영업이익 12.7억 원을 공개했고 글로벌·커머스 전환을 강조했다.

이 말은 개발 포지션이 단순 사내 챗봇 하나를 만드는 역할에 머물 가능성이 낮다는 뜻이다. **마케터·콘텐츠팀·크리에이터 운영팀이 반복적으로 처리하는 리서치, 보고서, 데이터 정리, 콘텐츠 운영, 캠페인 관리 흐름을 자동화할 여지**가 크다.

## 2-2. 데이터 기반 의사결정 성향

뷰스컴퍼니는 고려대학교 연구팀과 실제 운영 중인 뷰티 유튜브 채널 데이터를 활용한 연구를 진행했고, 대표는 50개 채널과 장기간 패널 데이터, 수천 편의 쇼츠 데이터를 분석해 단순 조회수보다 재방문 시청자의 시청시간 등 구조적인 지표를 강조했다.

또 회사는 매월 올리브영·다이소 트렌드 리포트를 발행한다.

### 면접에서 연결할 포인트

“LLM을 붙이면 무엇이든 좋아진다”가 아니라,

- 어떤 원천 데이터가 있는가?
- 사람이 지금 어떤 판단을 반복하고 있는가?
- LLM이 잘하는 부분과 규칙/SQL/Python이 잘하는 부분은 무엇인가?
- 결과가 틀렸을 때 어떤 피해가 생기는가?
- 어디에 사람 승인(Human-in-the-loop)을 남길 것인가?

를 먼저 보는 태도가 잘 맞는다.

## 2-3. 2026년 시점에서 보이는 성장 단계

공개 기업 DB(나이스디앤비 제공 정보가 노출된 인크루트) 기준 2025년 매출은 **166억 4,924만 원**, 순이익은 **10억 8,544만 원**으로 표시된다. 2024년 매출 136억 7,731만 원보다 성장한 수치다. 회사가 직접 공개한 2025년 상반기 자료에서도 매출 92.4억 원, 영업이익 12.7억 원을 밝혔고, 당시 핵심 방향을 **IP 기반 글로벌 커머스**로 설명했다.

이 숫자를 면접에서 과하게 외우는 것보다 중요한 해석은 다음이다.

- 작은 실험 단계의 회사가 아니라 **이미 돈을 버는 기존 사업 위에서 새 구조를 확장하는 단계**다.
- 광고 캠페인만 수행하는 조직보다 **콘텐츠 제작 → 크리에이터 운영 → 성과 데이터 → 커머스 전환 → 글로벌 유통**으로 업무 연결점이 많아지고 있다.
- 연결점이 많아질수록 사람이 복붙하고 확인하는 운영 비용도 같이 커질 가능성이 높다.
- 따라서 LLM 사내 자동화 개발자의 가치는 “멋진 챗봇”보다 **조직이 커져도 반복 업무와 정보 흐름이 같이 복잡해지지 않도록 운영 레버리지를 만드는 것**에 있다.

## 2-4. 다른 회사와 무엇이 다른가

면접에서 “다른 회사도 AI 자동화 많이 하는데 왜 뷰스인가요?”라는 질문에 대비해 비교축을 정리한다. 아래는 공개 사업 구조를 바탕으로 한 **비교 해석**이며, 특정 경쟁사를 깎아내리는 표현은 쓰지 않는다.

### 전통 광고대행사와의 차이

전통적 대행 모델은 캠페인 수주 → 제작/집행 → 결과 보고가 중심이기 쉽다. 뷰스컴퍼니는 공개 자료에서 **브랜드와 크리에이터를 함께 키우는 구조**, 콘텐츠 반복 제작, 팬덤, 커머스 전환까지 이어지는 흐름을 강조한다.

즉 자동화 대상도 단순 보고서 작성만이 아니라 **크리에이터/콘텐츠/브랜드/성과 데이터가 이어지는 내부 운영 흐름 전체**가 될 수 있다는 점이 흥미롭다.

### 일반 MCN과의 차이

일반적인 MCN을 “크리에이터 관리·광고 매칭”으로만 보면, 비라운드는 공개 자료상 **콘텐츠를 반복 생산하고 팬덤을 형성해 커머스로 연결하는 구조**를 강조한다. 다만 이번 조사에서는 **‘비라운드가 전체 매출의 40% 이상을 기여했다’는 수치를 신뢰 가능한 확정 사실로 사용하지 않기로 했다.**

면접에서의 포인트는 “MCN이라 재미있어서”가 아니라 **콘텐츠 운영이 반복 가능한 시스템이 될수록 데이터와 자동화가 사업 성과에 직접 연결될 수 있다**는 점이다.

### AI 제품회사와의 차이

AI SaaS 회사라면 AI 자체가 상품일 수 있다. 이 포지션은 공개 공고명부터 **‘LLM 사내 자동화’**다. 즉 모델 성능을 판매하는 것보다, 이미 존재하는 마케팅·콘텐츠·커머스 조직 안에서 **업무 시간을 줄이고 오류를 줄이며 의사결정 속도를 높이는 AI**가 더 중요할 가능성이 높다.

이 지점이 내가 만든 JK와 특히 잘 맞는다. 나는 “AI가 답을 잘하는가”보다 **AI가 실제 도구를 실행할 때 권한·상태·중복·실패 복구를 어떻게 다룰지**를 더 오래 고민해봤다.

## 2-5. 이 회사에서 자동화 ROI가 크게 날 것 같은 이유

공개 자료만 보고 가정하면 자동화 후보는 다음 네 종류로 나뉜다.

1. **리서치형**: 올리브영/다이소/소셜 트렌드 수집, 경쟁사·제품 변화 정리
2. **운영형**: 크리에이터/캠페인 상태 업데이트, 반복 입력, 파일/시트 정리
3. **분석형**: 캠페인 KPI 집계, 성과 비교, 이상치 탐지, 리포트 초안
4. **지식형**: 과거 캠페인·제안서·가이드·브랜드 이력 검색

이 네 가지는 모두 “LLM만 붙이면 되는 일”이 아니다. API/크롤링/DB/권한/스케줄러/검증 UI와 LLM이 함께 필요하다. 그래서 웹·백엔드·AI·자동화를 전부 건드려본 경험이 차별점이 될 수 있다.

# 3. 실제 JD와 회사 맞춤 업무 시나리오

## 3-1. 실제 JD에서 확정된 업무

1. **프롬프트 설계·관리·개선**: 개인 프롬프트가 아니라 반복 사용 가능한 템플릿, 버전, 평가 기준까지 관리
2. **워크플로 오케스트레이션**: 여러 LLM/코드/API/사내 도구 단계를 연결하고 실패·재시도를 제어
3. **출력 평가·검증**: “그럴듯함”이 아니라 정답성, 형식 준수, 근거 일치, 실패율 등을 측정
4. **텍스트 정제·분류·구조화**: 비정형 입력을 후속 시스템이 쓸 수 있는 스키마로 변환
5. **부서 반복 업무 자동화**: 현업 업무를 관찰해 deterministic code와 LLM의 경계를 정하고 실제 도구로 연결

## 3-2. 회사 맥락에서 연습할 업무 시나리오 — 추론

아래는 실제 내부 업무라고 단정하지 않고 **케이스 면접용 가정**으로만 사용한다.

### 반복 사무 업무 자동화 예시

- 엑셀/스프레드시트 정리와 요약
- 캠페인 성과 자료 자동 집계
- 보고서 초안 생성
- 회의록 → 액션 아이템 변환
- 메일/메신저/폼 입력 → 사내 DB나 시트 업데이트
- 브랜드/크리에이터 데이터 수집 후 정형화
- 반복 리서치 자동화

### LLM + 기존 시스템 연동

- Claude/GPT 계열 LLM API — JD 확인
- Slack/Notion/Google Workspace 연동 — JD 확인
- Structured Output/JSON Schema
- Tool calling / Function calling
- 사내 DB, Sheets, Drive, 메일, 외부 SaaS API 연결 — 구체 구성은 미확인
- Python/Node/TypeScript 기반 서버
- 간단한 React/Web UI
- 인증, 권한, 로그, 재시도

### 빠른 프로토타이핑 후 운영화

“바이브 코딩” 채용 문구상 가장 중요할 수 있다.

단순 데모를 만드는 능력보다 다음 전환이 중요하다.

**아이디어 → 1일 MVP → 현업 사용 → 실패 로그 수집 → 예외 처리 → 권한/비용/관측성 추가 → 운영 도구화**

### RAG/사내 지식검색

RAG 경험 자체는 JD 우대사항으로 확인됐다. 다만 실제 내부 문서 종류와 vector DB 사용 여부는 미확인이다. 캠페인 리포트·제안서·가이드 등을 대상으로 한 설계는 **면접 연습용 가정**으로 설명한다.

따라서 다음 질문이 나올 수 있다.

- “사내 문서를 챗봇으로 찾게 한다면 어떻게 만들 건가요?”
- “RAG와 그냥 긴 프롬프트의 차이는?”
- “검색 결과가 없을 때 어떻게 하나요?”
- “민감 문서 권한은 어떻게 막나요?”

### 웹 크롤링/리서치 자동화

회사 공개 활동상 트렌드/채널 데이터를 다루므로 연습 가치가 있지만, **크롤링 자체가 상세 JD에 명시됐다고 말하지 않는다.**

여기서 중요한 건 “크롤링 할 줄 압니다”가 아니라:

- 공식 API 우선
- robots/약관/개인정보 고려
- rate limit
- 변경 감지
- 중복 제거
- 스키마 정규화
- 실패 시 재시도와 partial result
- 출처/수집시각 저장

까지 말하는 것이다.

# 4. 내 프로젝트 중 무엇을 앞세울지

## 1순위: JK

이 직무와 가장 잘 맞는다.

### 왜 강한가

JK는 단순 챗봇이 아니라 **LLM/에이전트가 실제 도구를 안전하게 실행하는 자동화 하네스**에 가깝다.

말할 핵심:

- 자연어 요청을 실제 작업으로 연결
- 프로젝트별 도구/권한 분리
- 승인 필요한 작업은 Human-in-the-loop
- `pending → approved → running → succeeded/failed` 상태 관리
- 승인 이후 같은 작업이 중복 실행되지 않도록 job resume/idempotency 고민
- Windows/OCI 실행 환경 분리
- Git을 source of truth로 둬 충돌 방지
- 장기 작업을 goal loop로 쪼개고 검증

### 면접 한 줄

“LLM에게 명령만 잘 내리는 것보다, 실제 사내 자동화에서는 **권한·중복 실행·실패 복구·결과 추적**이 더 중요하다고 느껴 JK라는 실행 하네스를 직접 만들고 운영했습니다.”

## 2순위: LLM Wiki

### 왜 강한가

- 내부 문서 검색 문제를 직접 다룸
- RAG
- chunking
- 검색 인덱스
- hybrid retrieval
- 근거 기반 답변
- 검색 실패 시 abstention/fallback
- 평가셋/benchmark

### 면접 한 줄

“사내 문서를 LLM에 무작정 넣기보다, 검색 품질과 근거를 먼저 관리해야 한다고 판단해 문서 RAG와 검색 평가셋을 직접 만들었습니다.”

## 3순위: VibeCheck

### 왜 강한가

사내 자동화에서 자주 나오는 **외부 URL 처리 + 브라우저 자동화 + 비동기 작업 + 보안 경계**를 설명하기 좋다.

- URL 입력 → 분석 job
- 캡처/검증
- job 상태
- retry/recovery
- SSRF 방어
- rate limit
- 결과 리포트

### 면접 한 줄

“자동화는 성공 경로보다 외부 입력이 이상하거나 사이트가 느릴 때 어떻게 복구하는지가 중요해서 job 상태와 SSRF 같은 운영 이슈까지 함께 처리했습니다.”

LLM 직무와 직접적이지는 않지만 **실시간 시스템, event-driven backend, 책임 분리**를 보여준다.

- producer/consumer 분리
- backpressure

- timestamp consistency

웹 서비스 기본기 질문이 나올 때 사용한다.

## 4-1. 면접 답변을 관통할 ‘필살기 → 회사 문제 → 연결 → 캐릭터’ 구조

인스타식 표현을 그대로 베끼지 말고, 내 실제 경험에 맞게 사용한다.

### 공식

1. **내 필살기:** 기술 이름이 아니라 해결한 문제를 말한다.
2. **이 회사의 문제:** 공개 자료를 근거로 이 회사에서 왜 같은 문제가 중요할지 설명한다.
3. **그래서 내가:** 내 경험이 입사 후 어떤 업무에 전이될 수 있는지 말한다.
4. **한 줄 더:** 반복되는 나의 문제 해결 습관을 남긴다.

### 나쁜 예

“저는 RAG, MCP, MQTT, React, Python을 해봤고 새로운 기술을 빨리 배웁니다.”

기술 목록은 많지만 회사가 왜 나를 뽑아야 하는지가 없다.

### 좋은 예

“LLM이 실제 작업을 실행할 때 요청과 실행을 바로 붙이지 않고 권한·승인·job 상태를 분리해, 실패하거나 결과가 끊겨도 같은 작업이 중복 실행되지 않게 만든 경험이 있습니다. 뷰스컴퍼니처럼 여러 팀의 반복 업무와 외부 도구를 연결해 자동화하려면 한 연동의 실패가 전체 업무 흐름으로 번지지 않게 만드는 게 중요하다고 봤습니다. 저는 이미 그 실패를 직접 겪고 복구 구조까지 만들어봤기 때문에, 데모가 아니라 실제 현업에서 계속 쓰는 자동화를 만드는 데 기여할 수 있다고 생각합니다. **저는 보이는 오류를 바로 덮기보다 실패가 어느 경계에서 생기는지 먼저 분리하는 편입니다.**”

## 4-2. 내 필살기 1 — ‘LLM을 실행 가능한 업무로 바꾸되, 사고가 번지지 않게 분리한다’

### ① 내 필살기

JK에서 자연어 요청과 실제 실행 사이에 **도구 레이어, 프로젝트 권한, 승인, job 상태, 결과 resume**를 분리했다. 특히 승인 후 실제 job은 성공했는데 응답이 끊기면 같은 명령이 다시 실행되는 문제를 겪으며 idempotency와 resume이 왜 필요한지 직접 배웠다.

### ② 이 회사의 문제

사내 자동화가 늘면 Sheets/Docs/DB/메일/외부 API/LLM처럼 여러 연동이 붙는다. 이때 API 하나가 느리거나 응답이 유실됐다고 전체 업무를 다시 실행하면 **중복 발송, 중복 입력, 비용 증가, 데이터 오염**이 생길 수 있다.

### ③ 그래서 내가

“자동화가 된다”보다 **어디까지 자동으로 실행하고, 어디서 승인받고, 실패했을 때 어디서부터 재개할지**를 설계해본 경험을 가져갈 수 있다.

### ④ 한 줄 더

**“저는 정상 경로보다 실패했을 때 어디까지 영향이 번지는지를 먼저 봅니다.”**

## 4-3. 내 필살기 2 — ‘LLM 답변보다 근거를 먼저 관리한다’

### ① 내 필살기

LLM Wiki에서 문서가 늘어날수록 “모델이 똑똑하면 찾겠지”가 통하지 않아, Markdown 구조 기반 chunking, lexical/vector 검색, 검색 평가, fallback을 직접 다뤘다. 실제로 자연어 검색이 특정 말투에서 0건이 되는 문제도 재현 질의와 테스트를 추가해 검색 guard를 수정했다.

### ② 이 회사의 문제

뷰스컴퍼니는 콘텐츠/캠페인/크리에이터/브랜드 데이터가 쌓이고, 데이터 기반 연구와 트렌드 리포트도 공개적으로 진행한다. 이 환경에서 AI가 그럴듯하게 틀린 과거 사례를 가져오면 현업 신뢰를 빠르게 잃는다.

### ③ 그래서 내가

사내 지식검색을 만들 때 “챗봇부터”가 아니라 **source freshness, retrieval 품질, 근거 링크, 검색 실패 시 abstention**부터 설계할 수 있다.

### ④ 한 줄 더

**“답이 이상하면 프롬프트를 먼저 만지기보다, 모델이 어떤 근거를 보고 답했는지부터 확인합니다.”**

## 4-4. 내 필살기 3 — ‘실시간 이벤트를 느슨하게 연결해봤다’

### ① 내 필살기

스마트 안전 관제에서 AI 탐지 → MQTT 이벤트 → Spring Backend → React 관제 화면으로 역할을 분리했다. 모델 추론과 알림/저장/UI를 한 프로세스에 묶지 않고 이벤트 경계로 나눴다.

### ② 이 회사의 문제

마케팅·콘텐츠 자동화도 외부 플랫폼 API, 크롤러, 분석기, LLM, 리포트 발행이 한 번에 연결될 수 있다. 한 단계가 실패했다고 이미 수집한 데이터나 앞 단계까지 버릴 필요는 없다.

### ③ 그래서 내가

Kafka 실무 경험을 과장하지 않는다. 대신 **producer/consumer 분리, 비동기 이벤트, retry, idempotency, 상태 추적**이라는 설계 문제를 다른 메시징 시스템에서 직접 다뤘고, Kafka가 필요해지면 그 개념을 빠르게 전이할 수 있다고 말한다.

### ④ 한 줄 더

**“도구 이름보다 시스템 경계를 왜 나눴는지를 설명할 수 있는 개발자이고 싶습니다.”**

## 4-5. 결국 ‘왜 나를 뽑아야 하는가’

경력 연차로만 경쟁하면 더 오래 일한 지원자가 당연히 많다. 따라서 답을 “제가 더 뛰어납니다”로 만들지 않는다. **이 포지션이 지금 필요로 할 가능성이 높은 문제를 이미 여러 각도에서 풀어봤다**고 말한다.

### 30초 답변

“저보다 실무 연차가 긴 지원자는 분명 많을 거라고 생각합니다. 대신 저는 이번 포지션에서 필요한 문제를 꽤 직접적으로 만들어보고 깨뜨려봤습니다. JK에서는 LLM이 실제 작업을 할 때 권한과 job 상태, 중복 실행을 다뤘고, LLM Wiki에서는 사내 문서를 근거 있게 찾는 RAG와 검색 평가를 만들었습니다. 또 실시간 관제에서는 이벤트 기반으로 시스템을 분리해 운영했습니다. 그래서 저는 AI 기능 하나를 만드는 사람보다 **현업 업무를 듣고, 자동화할 경계를 정하고, 실패해도 운영되는 흐름까지 끝까지 만드는 사람**으로 기여할 수 있다고 생각합니다.”

### 10초 압축

**“LLM을 써본 사람이 아니라, LLM을 실제 업무에 붙였을 때 생기는 권한·검색·중복·실패 문제를 이미 겪어본 사람이라는 점이 제 차별점입니다.”**

### 남길 캐릭터 한 줄 후보

- **문제를 바로 해결하기보다, 먼저 진짜 실패 지점을 찾는 데 자신이 있습니다.**
- **기능이 안 되면 코드를 더 붙이기보다, 어느 경계의 책임인지부터 나눕니다.**
- **빠르게 만들되, 실제로 쓰기 시작하는 순간부터는 실패 복구와 검증을 제품의 일부로 봅니다.**
- **AI가 만든 결과도 운영 환경에서는 그냥 하나의 외부 입력이라고 생각합니다.**

# 5. 가장 나올 가능성이 높은 핵심 면접 질문 — 외우지 말고 말로 풀기

## 5-0. 실제 제출 서류 기준으로 먼저 맞아야 할 질문

뷰스컴퍼니 면접 후기를 보면 같은 면접도 사람에 따라 “무난했다”와 “어려웠다”가 갈렸고, 회사 채용 메시지에서도 **스스로 고민하고 선택한 이유를 설명하는 것**이 중요하게 보인다. 그래서 아래 질문은 단순 기술 퀴즈보다 우선순위를 높게 잡는다.

### A급 — 거의 반드시 방어 준비

#### 1) “JK를 왜 만들었어요? 그냥 ChatGPT/Codex 쓰면 되는 거 아닌가요?”

**서류에서 물리는 문장:** `ChatGPT 웹 세션 기반 Thin Harness`, `별도 LLM 호출 없이 실행환경 연결`

**기억할 말:** `추론 중복 줄임 → 실행 계층만 분리 → 권한/승인은 모델 밖`

“처음부터 또 하나의 코딩 에이전트를 만들려던 건 아니었습니다. 이미 ChatGPT 웹 세션에서 추론하고 있는데 같은 작업을 위해 별도 모델을 또 호출하는 건 중복이라고 봤습니다. 그래서 JK는 추론을 다시 하지 않고 프로젝트 컨텍스트, 권한, 승인, 실제 실행 상태만 연결하는 얇은 계층으로 범위를 잡았습니다. 실제로 써보니 모델 성능보다 승인 이후 job 상태나 중복 실행 같은 운영 문제가 더 크게 보여서 그쪽을 많이 고쳤습니다.”

**꼬리질문:** Thin Harness의 장단점은? 웹 세션이 끊기면? API 기반 agent와 비교하면? 왜 MCP 형태인가? 권한 검사는 어디서 하나?

#### 2) “포트폴리오에서 AI가 만든 것과 본인이 만든 걸 정확히 나눠보세요.”

**서류에서 물리는 문장:** `LLM-assisted Build → Human Decision → QA → Deploy`

**기억할 말:** `반복 구현은 AI → 구조/데이터/권한은 직접 → 결과는 테스트로 확인`

“LLM은 초안 코드나 반복 구현 속도를 높이는 데 적극적으로 썼습니다. 대신 어떤 구조로 나눌지, 데이터가 어디서 어디로 흐를지, 권한과 승인 경계를 어디에 둘지는 제가 정했습니다. 생성 결과도 그대로 채택하지 않고 diff, 테스트, 로그, 실제 배포 결과를 보고 판단했습니다. 그래서 제 포트폴리오에서 보여주고 싶은 건 ‘AI가 코드를 많이 써줬다’보다 AI를 써도 제가 어떤 판단을 책임졌는지입니다.”

**꼬리질문:** 모르는 코드도 merge했나? AI 때문에 난 장애는? 테스트는 누가 만들었나? AI 없이도 유지보수 가능한가?

#### 3) “LLM Wiki에서 왜 Hybrid Search가 제일 좋았나요?”

**서류에서 물리는 숫자:** `50개 문서 / 737개 Chunk / 61개 Golden Query / Hybrid Hit@5 82.14%`

**기억할 말:** `BM25는 정확한 단어 → Vector는 의미 → RRF로 둘을 합침`

“프로젝트 문서는 기술명이나 에러 메시지처럼 정확한 키워드가 중요한 질문도 있고, 같은 의미를 다른 표현으로 묻는 질문도 있었습니다. 그래서 BM25 하나나 vector 하나보다 둘을 같이 쓰는 게 맞다고 봤고, RRF로 순위를 합쳤습니다. 제출 당시 평가셋에서는 Hybrid Hit@5가 82.14%로 가장 높았습니다. 중요한 건 숫자 자체보다 같은 61개 Golden Query로 방식을 바꿀 때마다 다시 비교했다는 점입니다.”

**꼬리질문:** Hit@5가 정확히 뭔가? Recall@5와 차이는? MRR은? 왜 RRF인가? reranker는 왜 안 썼나? Golden Query는 어떻게 만들었나?

#### 4) “61개 Golden Query는 어떻게 만들었어요? 좋은 평가셋이라고 볼 수 있나요?”

**기억할 말:** `실제 찾고 싶은 질문 → 정답 문서 지정 → 실패 질문도 포함`

“제가 실제 프로젝트 문서를 찾을 때 쓸 법한 질문을 기준으로 잡고, 각 질문에 어떤 문서가 정답 근거인지 연결했습니다. 같은 질문을 BM25, Vector, Hybrid에 반복해서 넣어 비교했습니다. 완벽한 대규모 benchmark라고 주장하지는 않고, 제 문서 검색 구조를 바꿀 때 regression을 잡는 프로젝트 내부 평가셋이라고 보는 게 맞습니다.”

**꼬리질문:** 평가셋 편향은? 질문 수가 충분한가? answerable/unanswerable은? 새로운 문서가 들어오면 어떻게 갱신하나?

#### 5) “지금 LLM Wiki 숫자랑 포트폴리오 숫자가 다른데요?”

**기억할 말:** `제출 당시 스냅샷 → 이후 문서 추가/인덱스 재생성 → 당시 수치는 당시 조건으로 유효`

“포트폴리오 수치는 제출 자료를 만들 당시 스냅샷입니다. 그 뒤에도 문서를 추가하고 검색 구조를 계속 수정해서 현재 문서 수나 chunk 수는 달라졌습니다. 그래서 면접에서는 제출 당시 비교 결과와 현재 운영 상태를 섞지 않고 설명하겠습니다. 당시 Hybrid 82.14%는 그 시점의 50개 문서, 737개 chunk, 61개 평가질의 조건에서 나온 결과입니다.”

**주의:** 최신 수치로 제출 자료를 소급해서 바꿔 말하지 않는다.

#### 6) “스마트 안전관제에서 ID Switch 8회를 1회로 어떻게 줄였어요?”

**기억할 말:** `낙상 때 형태 급변 → 기존 매칭 실패 → 예외 상황에서 위치/이동 흐름 보조`

“처음에는 tracker 파라미터만 계속 바꿨는데 결과가 일관되지 않았습니다. 로그와 영상 구간을 같이 보니까 사람이 넘어지는 순간 bbox 형태와 위치가 급격히 변하면서 기존 매칭이 끊기는 구간이 반복됐습니다. 그래서 전체 tracker를 바꾼 게 아니라 그 예외 상황에서만 위치와 이동 흐름을 추가로 보고 재연결하도록 범위를 좁혔고, 같은 자체 테스트 영상에서 ID Switch가 8회에서 1회로 줄었습니다.”

**꼬리질문:** Ground Truth 기반 지표인가? 왜 ByteTrack을 썼나? 다른 영상에서도 같은가? purity가 떨어지는 trade-off는?

#### 7) “행동 분류 F1 89.29% → 93.49%는 뭘 바꿔서 오른 건가요?”

**기억할 말:** `정적 좌표만 보지 않음 → motion feature 추가 → 동일 평가에서 비교`

“Pose keypoint의 한 시점 좌표만 보는 것보다 낙상처럼 움직임의 변화가 중요한 행동은 속도나 기울기 정보가 필요하다고 봤습니다. 그래서 motion feature를 포함한 54차원 입력으로 확장했고 같은 평가 조건에서 F1이 89.29%에서 93.49%로 올라갔습니다. 이때 false negative와 false positive도 같이 줄어드는지 확인했습니다.”

**꼬리질문:** 54차원 구성은? sequence length는? 과적합은? F1을 왜 봤나?

#### 8) “전체 처리 지연 11.789ms → 6.101ms는 end-to-end인가요?”

**기억할 말:** `아님 → 2-cam RTSP 처리 benchmark → TensorRT 비교`

## Q13. 어떤 업무는 LLM을 쓰면 안 되나요?

“규칙이 명확한 계산이나 필터링은 LLM을 쓸 이유가 없다고 봅니다. LLM은 요약이나 분류처럼 자연어 판단이 필요한 좁은 구간에 쓰고, 돈이나 삭제, 외부 발송처럼 되돌리기 어려운 일은 일반 코드의 규칙과 사람 승인으로 감싸겠습니다.”

## Q14. Python과 TypeScript 중 무엇을 쓰겠나요?

**기억할 말:** `데이터/배치면 Python → 웹 흐름이면 TS → 기존 팀 스택 우선`

“둘 다 목적에 맞춰 쓸 것 같습니다. 데이터 처리나 배치, AI SDK 쪽은 Python이 편한 경우가 많고, 웹 앱이나 Node API에서 프론트까지 타입을 공유하려면 TypeScript가 좋습니다. 다만 새로 들어가서 제 취향대로 정하기보다 팀의 기존 시스템을 먼저 보겠습니다.”

## Q15. 크롤링 자동화를 설계해 보세요.

**기억할 말:** `API 먼저 → 원본/출처 저장 → LLM은 마지막`

“먼저 공식 API가 있는지 확인합니다. 수집이 필요하면 원본을 바로 버리지 않고 source URL과 수집 시각을 같이 저장하고, parser와 정규화 단계를 분리합니다. 중복 제거와 rate limit, retry도 넣고요. LLM은 수집기 자체보다 마지막 요약이나 분류처럼 필요한 부분에만 쓰겠습니다.”

## Q16. 마케팅팀의 주간 리포트 작성을 자동화한다면?

**기억할 말:** `숫자는 코드 → 설명만 LLM → 사람이 보고 발송`

“데이터부터 수집해서 같은 형식으로 정리하고 KPI 계산은 코드로 하겠습니다. LLM한테 숫자 계산까지 맡기기보다 이미 계산된 결과를 설명하고 초안을 쓰게 합니다. 초안에는 근거 링크를 붙이고 담당자가 확인한 뒤 Docs나 Slack으로 보내는 구조가 좋다고 생각합니다.”

## Q17. 비개발 직군의 요구사항이 모호하면 어떻게 하나요?

**기억할 말:** `원하는 기능 묻지 않음 → 일하는 걸 봄 → 작은 구간부터`

“처음부터 어떤 기능이 필요하냐고만 물으면 서로 다르게 이해할 수 있어서, 지금 그 일을 실제로 한 번 보여달라고 할 것 같습니다. 어디서 데이터를 받고 뭘 판단하고 어디에 옮기는지를 본 다음, 반복이 많고 실패해도 위험이 낮은 구간부터 자동화하겠습니다.”

## Q18. 실패한 프로젝트/실수 경험은?

**기억할 말:** `WebRTC 선택 → 실제 프리즈 → 목적 보고 MJPEG 복귀`

“스마트 안전 관제에서 처음엔 WebRTC나 HLS가 구조적으로 더 좋아 보여서 꽤 오래 붙잡았습니다. 그런데 실제 환경에서는 프리즈와 인코더 종료가 반복됐고, 우리 목표는 최신 스트리밍 기술을 쓰는 게 아니라 관제 화면을 안정적으로 보여주는 거였습니다. 그래서 결국 MJPEG로 돌아갔습니다. 그 뒤로는 기술 선택할 때 성공 기준이랑 철회 기준을 먼저 정하려고 합니다.”

## Q19. AI가 생성한 코드 품질은 어떻게 유지하나요?

**기억할 말:** `작게 생성 → diff/test → 실제 실행 확인`

“한 번에 큰 기능을 맡기지 않고 diff가 검토 가능한 크기로 쪼갭니다. 생성 코드도 일반 코드랑 똑같이 lint, typecheck, 테스트를 거치고 secret이나 dependency도 확인합니다. 저는 배포까지 하는 프로젝트라면 build 성공에서 끝내지 않고 실제 도메인이나 runtime에서 동작하는지도 확인합니다.”

## Q20. 입사하면 첫 자동화 과제로 무엇을 해보고 싶나요?

**기억할 말:** `현업 먼저 → 후보 점수화 → 1~2주짜리 MVP`

“입사하자마자 큰 에이전트를 만들지는 않을 것 같습니다. 먼저 각 팀에서 반복 시간이 많이 드는 일을 몇 개 보고, 빈도랑 시간, 오류 비용, 구현 난이도로 우선순위를 잡겠습니다. 공개 자료만 보면 트렌드 리포트나 캠페인 성과 정리가 떠오르지만 실제 업무를 본 뒤 1~2주 안에 효과를 확인할 수 있는 작은 자동화부터 해보고 싶습니다.”

## Q21. 다른 마케팅 회사가 아니라 왜 뷰스컴퍼니인가요?

**기억할 말:** `콘텐츠/IP → 데이터 활용 → 자동화가 성장 레버리지`

“단순히 마케팅 회사라서 지원한 건 아닙니다. 공개 자료를 보니까 뷰스는 브랜드, 크리에이터, 콘텐츠를 따로 보지 않고 팬덤이나 커머스까지 이어가려는 방향이 보였고 실제 데이터 연구나 트렌드 리포트도 하고 있었습니다. 이런 구조면 자동화가 그냥 편의 기능이 아니라 팀 사이 정보가 빨리 흐르게 만드는 도구가 될 수 있겠다고 생각했습니다.”

## Q22. 더 경력 많은 지원자 대신 왜 본인을 뽑아야 하나요?

**기억할 말:** `연차는 인정 → 직무 문제를 이미 겪음 → 직접 만들고 고침`

“연차만 보면 저보다 긴 분들이 많을 거라고 생각합니다. 대신 이번 역할에서 실제로 생길 법한 문제를 꽤 직접 겪었습니다. JK에서는 권한과 중복 실행을 다뤘고, LLM Wiki에서는 검색 근거와 평가를 만들었고, 이걸 실제로 배포하면서 장애도 다시 고쳐봤습니다. 그래서 처음부터 완벽한 요구사항을 기다리기보다 현업 일을 보고 작게 만들어서 운영까지 가져가는 쪽에서 빠르게 기여할 수 있다고 생각합니다.”

## Q23. 뷰스컴퍼니에서 LLM 자동화가 실패한다면 가장 흔한 이유는 뭐라고 보나요?

**기억할 말:** `업무를 잘못 고름 → 데이터/권한 엉킴 → 현업이 안 씀`

“모델이 조금 틀리는 것보다 자동화할 문제를 잘못 고르는 게 더 큰 실패라고 생각합니다. 입력 데이터나 권한이 정리되지 않은 상태에서 LLM부터 붙이거나, 사람이 어디서 확인해야 하는지도 안 정하면 현업이 금방 안 쓰게 될 것 같습니다. 그래서 실제 업무를 먼저 보고 코드로 고정할 부분과 LLM 판단이 필요한 부분을 나눈 다음, 시간 절감이나 수정률, 실패율을 계속 보겠습니다.”

# 6. 회사 맞춤 시스템 디자인: ‘뷰티 트렌드 리포트 자동화’

이건 “제가 입사하면 무조건 이걸 만들겠습니다”가 아니라 **회사 공개 활동에서 착안한 면접용 사고실험**이다.

## 문제 가정

마케터가 매월 올리브영/다이소/소셜 채널을 조사해 신제품·프로모션·카테고리 변화를 정리하고 리포트를 만든다.

## 나쁜 자동화

`웹 전체 크롤링 → 모든 HTML을 LLM에 넣음 → 보고서 자동 생성 → 바로 발행`

문제:

- 비용 큼
- 출처 불명확
- 숫자 오류
- 중복
- 사이트 변경에 취약
- 법/약관 이슈
- hallucination

## 더 나은 구조

### 1. Source Registry

수집 대상, 공식 API 여부, URL, 수집 주기, 약관/robots 메모를 관리한다.

### 2. Ingestion

API 또는 허용 범위 내 수집기로 raw data를 가져온다.

### 3. Normalization

제품명, 브랜드, 카테고리, 가격, 프로모션, 날짜, source URL을 정형 스키마로 만든다.

### 4. Deterministic Analysis

신제품 수, 가격 변화, 카테고리별 빈도 같은 수치는 SQL/Python으로 계산한다.

### 5. LLM Layer

LLM은 다음에만 사용한다.

- 비슷한 프로모션 묶기
- 변화 요약
- 카테고리 설명 초안
- 제목 후보

### 6. Evidence

각 문장/표에 source URL과 수집 시각을 남긴다.

### 7. Human Review

외부 공개 전 마케터가 변경점을 확인하고 승인한다.

### 8. Evaluation

- 리포트 작성 시간 감소
- 수정 문장 비율
- source mismatch 비율
- hallucination 건수
- 수집 실패율
- 1회 리포트당 비용

### 면접에서 한 줄

“LLM에게 리포트를 쓰게 하는 게 목표가 아니라, 사람이 6시간 하던 수집·정리·초안 작업을 1시간 검수 작업으로 바꾸는 게 목표입니다.”

# 7. LLM/자동화 CS 압축 정리

## LLM

### Temperature

출력 다양성을 조절한다. 업무 자동화/정형 출력은 일반적으로 낮은 temperature가 유리하다.

### Context Window

한 번의 요청에 넣을 수 있는 token 범위. 크다고 모든 문서를 넣는 것이 좋은 건 아니다. 관련 문서만 retrieval하는 편이 비용·정확성에 유리할 수 있다.

### Structured Output

자유 텍스트 대신 schema에 맞는 JSON을 요구한다. 후속 코드가 안정적으로 파싱하기 좋다. 다만 **schema를 만족했다는 것과 내용이 사실이라는 것은 별개**다. 형식 검증 뒤에도 근거 일치·값 범위·업무 규칙 검증이 필요하다.

### Tool Calling

LLM이 직접 DB/메일을 만지는 것이 아니라, 사용할 도구와 인자를 선택하고 애플리케이션이 검증 후 실행하는 구조다.

## 실제 JD 기준 워크플로 설계 원칙

### Deterministic workflow vs 제한적 Agent

- 규칙·계산·필터·변환처럼 결과가 명확한 단계는 **일반 코드**로 고정한다.
- 요약·분류·초안·애매한 자연어 해석처럼 확률적 판단이 필요한 좁은 단계에만 LLM을 둔다.
- 에이전트에게 도구 선택권을 주더라도 **허용 도구, 호출 횟수, 비용, 시간, side effect 범위**를 제한한다.
- 삭제·발송·외부 게시·권한 변경처럼 되돌리기 어려운 작업은 모델 판단만으로 실행하지 않는다.

### 추천 사내 자동화 파이프라인

`입력/원천 데이터 → deterministic 전처리 → LLM 변환/분류 → schema validation → eval/업무규칙 검증 → 필요 시 사람 승인 → 외부 시스템 write → audit log/rollback`

이 구조는 이번 실제 JD의 **프롬프트 관리 + 오케스트레이션 + eval + 텍스트 구조화 + 부서 자동화**를 한 번에 설명하기 좋다.

### LLM Eval

평가를 “좋아 보인다”로 끝내지 않는다. 업무에 맞춰 다음을 나눈다.

- **형식**: schema pass rate
- **정확성**: 정답셋/업무 규칙 대비 accuracy·precision/recall 등
- **근거성**: source attribution / source mismatch
- **운영성**: latency, 실패율, 재시도율, cost
- **현업 품질**: 수정률, 승인 거절률, 처리시간 절감
- prompt/model/version을 함께 기록해 회귀를 비교한다.

### 권한·승인·로그·롤백은 모델 밖에 둔다

LLM이 “실행해도 된다”고 출력했다고 권한이 생기는 것은 아니다. 사용자 ACL, tool allowlist, 승인 여부, idempotency, audit log, rollback은 **애플리케이션 계층**에서 강제해야 한다. 이 포인트는 JK 경험과 가장 직접적으로 연결한다.

## RAG

### Embedding

텍스트 의미를 vector로 표현한다.

### Cosine Similarity

두 vector 방향이 얼마나 비슷한지 보는 지표.

### BM25

키워드 기반 relevance 검색. 제품명/고유명사/정확한 기술어에 강한 경우가 있다.

### Hybrid Search

Vector + lexical 검색을 결합한다.

### Reranker

1차 검색 후보를 더 비싼 모델로 다시 정렬한다.

## Backend/Automation

### Idempotency

같은 요청이 반복되어도 side effect가 한 번만 일어나도록 설계하는 성질.

### Retry

실패 원인이 일시적인 경우 다시 시도. 모든 오류를 retry하면 안 된다.

### Exponential Backoff

재시도 간격을 점점 늘려 서버/외부 API에 과부하를 주지 않는다.

### Queue

느린 작업을 요청-response와 분리해 비동기로 처리한다.

### Webhook

외부 시스템의 이벤트가 발생했을 때 우리 서버 URL로 callback을 받는 방식.

### Rate Limit

단위 시간당 요청 수를 제한한다.

### Circuit Breaker

외부 서비스가 계속 실패할 때 호출을 잠시 차단해 연쇄 장애를 막는 패턴.

### Observability

log, metric, trace로 “무엇이 실패했고 어디서 느린지” 추적 가능하게 만드는 것.

## 보안·법규를 기술 설계에 연결하는 법

면접에서는 법 조문을 암기하기보다 **자동화 설계에서 무엇을 막을 것인지** 말한다. 아래는 법률 자문이 아니라 시스템 설계 관점의 체크포인트다.

- **개인정보보호법**: 목적에 필요한 데이터만 수집, 최소권한, 접근·처리 로그, 외부 LLM 전송 범위와 보존정책 확인
- **표시·광고 관련 규제**: LLM이 제품 성과·후기·광고 표현을 임의 생성하지 않게 근거와 승인 단계를 둠
- **화장품 관련 규제**: 효능·효과처럼 규제 민감한 표현은 생성 모델 단독 확정 금지, 허용 근거/가이드와 사람 검수 연결
- **저작권**: 크리에이터 이미지·영상·카피를 재사용하거나 학습/가공할 때 권리와 출처를 확인
- **근로 관련 업무**: 직원 평가·근태·인사처럼 사람에게 영향을 주는 자동화는 모델 단독 의사결정보다 정책·권한·사람 검토를 우선

이번 ULW research에서는 n8n, LlamaIndex, Haystack, Instructor의 구현 사례도 특정 버전/SHA 기준으로 조사했다. **면접에서는 라이브러리 이름을 외우기보다 재현 가능한 버전 고정과 변경 검증이 왜 필요한지** 설명한다.

# 9. 인성/경험 질문: 뷰스컴퍼니 스타일로 준비

공개 채용 글과 대표 메시지에서 반복 확인되는 선호는 **빠른 실행과 개선, 스스로 문제를 정의하는 태도, 끝까지 책임지는 자세, 새로운 AI 도구를 먼저 실험하는 성향**이다. 이는 **공개된 채용 선호 신호**이지, 현재 조직 전체의 문화라고 일반화하지 않는다.

또 2024년 AE 실제 면접 후기와 JobPlanet 공개 집계에서는 **지원동기, 회사 조사 수준, 직무·도메인 적합성, 경력 이동 사유, 업무 강도·입사 가능 시점** 같은 질문 신호가 확인됐다. 다른 직무의 과거 사례이므로 예상 질문 참고용으로만 사용한다.

반대로 **현재 LLM 자동화 포지션의 기술면접 또는 코딩테스트 실시 여부는 공개 근거가 없어 미확인**이다.

따라서 아래 질문은 모두 결과보다 판단 과정을 준비한다.

## Q. 남들이 시켜서가 아니라 스스로 개선한 경험이 있나요?

JK 하네스, 승인 UX, 배포 안정화 중 하나.

## Q. 본인이 내린 기술 선택이 틀렸던 적은?

WebRTC/HLS 고집 → 시연 안정성을 위해 MJPEG rollback.

포인트는 “실패했지만 열심히 했다”가 아니라 **무슨 evidence 때문에 판단을 바꿨는지**다.

## Q. 프로젝트를 끝까지 책임진 경험은?

스마트 안전 관제 팀장 경험 또는 JK 운영.

## Q. 속도와 완성도 중 무엇이 더 중요하나요?

“단계가 다르다.”

- discovery/MVP: 속도
- side effect/production: 검증과 안정성
- 운영: feedback loop

## Q. 모르는 기술을 급하게 써야 하면?

1. 작은 spike
2. 공식 문서
3. 최소 예제
4. 실패 조건 확인
5. sandbox
6. 실제 서비스 적용 전 test/rollback

## Q. AI를 많이 쓰면 본인 실력은 어떻게 증명하나요?

좋은 답:

“코드 타이핑 속도보다 문제를 쪼개는 기준, 생성 결과를 검증하는 능력, 운영 중 실패를 해석하고 복구하는 능력이 제 책임이라고 봅니다. 제가 만든 시스템에서는 LLM이 낸 결과도 테스트와 실행 권한 경계를 통과해야 실제 작업이 됩니다.”

# 12. 면접관이 파고들기 쉬운 약점과 대응

## “경력 1년 이상인데 실무 경력이 부족한 것 아닌가요?”

회피하지 않는다.

“정규직 실무 연차 기준으로는 부족합니다. 대신 실제 배포·운영하는 개인 프로젝트와 팀 프로젝트에서 요구사항 정의부터 장애 대응까지 직접 해 왔습니다. 그래서 연차를 과장하기보다 제가 실제로 판단하고 책임진 범위를 코드와 결과로 보여드리겠습니다.”

## “프로젝트가 너무 많은데 깊이가 있나요?”

“모든 프로젝트를 같은 깊이로 주장하지 않습니다. 면접에서는 JK, LLM Wiki, 스마트 안전 관제 3개만 중심으로 설명하고, 나머지는 특정 문제를 검증한 실험/서비스로 구분하겠습니다.”

## “AI 코딩 도구 의존도가 높은 것 아닌가요?”

“맞습니다. AI를 적극적으로 사용합니다. 대신 생성 결과를 그대로 신뢰하지 않고 요구사항·diff·test·runtime proof를 분리합니다. 실제로 AI 자동화 하네스를 만들며 생성보다 검증과 복구에 더 많은 기능을 넣었습니다.”

# 16. HR·인성 면접 — 키워드만 외우고 내 말로 답하기

여기는 완성 문장을 통째로 외우지 않는다. **내 성향 1개 + 실제 경험 1개 + 지금 어떻게 일하는지 1개**만 연결한다. 답이 너무 반듯해지면 오히려 외운 티가 난다.

## 16-1. 30초 자기소개

**기억할 말:** `AI를 실제 일에 붙임 → JK/RAG → 실패까지 봄`

“안녕하세요. 저는 AI를 실제 업무에 붙였을 때 생기는 문제를 해결하는 쪽에 관심이 많은 개발자 안진경입니다. JK에서는 권한이나 중복 실행 문제를 다뤘고, LLM Wiki에서는 검색 근거와 RAG를 만들었습니다. 기능을 빨리 만드는 것도 좋아하지만, 실제로 쓰기 시작했을 때 어디서 깨지는지까지 보는 편입니다.”

## 16-2. 1분 자기소개

**기억할 순서:** `관제에서 시스템 연결 → JK에서 실행 안정성 → Wiki에서 근거 → 뷰스 직무`

30초 자기소개에 다음 정도만 붙인다.

“처음에는 의료영상 AI처럼 모델 쪽에서 시작했는데, 스마트 안전 관제를 하면서 모델 결과가 실제 서비스까지 어떻게 이어지는지에 관심이 커졌습니다. 이후 JK와 LLM Wiki를 만들면서 LLM 실행의 권한·상태, RAG 검색 근거 같은 문제를 직접 다뤘습니다. 그래서 지금은 모델 하나를 잘 만드는 것보다 현업 업무를 보고 어디를 자동화할지 정하고 운영까지 가져가는 개발자로 일하고 싶습니다.”

## 16-3. 본인의 강점은 무엇인가요? — 3개만 고정

### 강점 1. 보이는 오류보다 진짜 원인을 먼저 찾는다

**기억할 말:** `재현 → 진짜 실패 지점 → 그다음 수정`

“문제가 생기면 바로 코드를 더 붙이기보다 일단 똑같이 재현해보는 편입니다. LLM Wiki 검색이 특정 말투에서 0건이 되던 것도 동의어를 무작정 늘리기보다 검색 조건이 대화체 표현까지 필수 키워드로 잡고 있다는 걸 찾아서 고쳤습니다. 그래서 증상보다 원인을 나눠보는 게 제 강점이라고 생각합니다.”

### 강점 2. 실패가 다른 영역으로 번지지 않게 경계를 나눈다

**기억할 말:** `한 덩어리로 안 묶음 → 경계 나눔 → 한 곳 실패가 전체로 안 번짐`

“기능을 한 덩어리로 묶기보다 책임을 나누는 편입니다. 관제에서는 AI와 백엔드를 MQTT 이벤트로 분리했고, JK에서도 요청과 실제 실행 사이에 승인과 job 상태를 따로 뒀습니다. 여러 API가 붙는 자동화에서도 한 단계가 실패했다고 전체를 다시 돌리지 않게 만드는 데 도움이 될 것 같습니다.”

### 강점 3. 운영 증거가 나올 때까지 끝낸다

**기억할 말:** `로컬 성공으로 안 끝냄 → 배포 → 실제 환경 확인`

“로컬에서 한 번 되는 걸 완료라고 생각하지 않는 편입니다. 테스트랑 build를 보고 배포한 뒤 실제 도메인에서도 새 버전이 뜨는지 확인합니다. 제가 만들었다는 말보다 실제로 돌아가는 상태를 남기는 걸 좋아합니다.”

### 10초 압축

**“원인을 먼저 찾고, 실패가 번지지 않게 나누고, 실제로 돌아가는 데까지 보는 편입니다.”**

## 16-4. 본인의 약점은 무엇인가요?

### 약점 1. 흥미로운 문제는 범위를 넓히는 경향이 있다

**기억할 말:** `옆 문제까지 손댐 → 범위 커짐 → 종료 조건 먼저`

“문제를 하나 보면 주변 것도 같이 고치고 싶어져서 범위가 커질 때가 있습니다. 개인 프로젝트에서 특히 많이 느꼈습니다. 그래서 요즘은 시작 전에 이번 작업이 어디까지 되면 끝인지 먼저 정하고, 추가로 보이는 건 backlog로 빼려고 합니다.”

### 약점 2. 확신이 부족하면 검증을 오래 하는 편이다

**기억할 말:** `비교 오래 함 → WebRTC 경험 → 되돌릴 수 있으면 빨리 결정`

“틀린 선택을 줄이려고 비교를 오래 하는 편도 있습니다. 관제 프로젝트에서 영상 전송 방식을 꽤 오래 실험했던 게 그런 경우였습니다. 지금은 쉽게 되돌릴 수 있는 건 작은 테스트만 하고 빨리 결정하고, 되돌리기 어려운 선택만 깊게 보는 기준을 두고 있습니다.”

피해야 할 답은 “완벽주의라 너무 열심히 한다”, “책임감이 너무 강하다”처럼 약점을 장점으로 위장하는 표현이다.

## 16-5. 성격의 장단점은?

**기억할 말:** `원인을 파고듦 ↔ 너무 넓어질 수 있음 → 종료 조건`

“문제가 생겼을 때 그냥 넘어가기보다 원인을 확인하는 편인 게 장점입니다. 반대로 보다 보면 주변 문제까지 손대서 범위가 커질 수 있습니다. 그래서 요즘은 지금 꼭 고칠 것과 나중에 개선할 걸 먼저 나누려고 합니다.”

## 16-6. 협업할 때 어떤 스타일인가요?

**기억할 말:** `내 코드만 보지 않음 → 입력/출력 맞춤 → 사람보다 인터페이스 확인`

“제가 맡은 부분만 끝내기보다 앞뒤 팀이랑 입력과 출력을 먼저 맞추는 편입니다. 관제 프로젝트에서도 AI가 어떤 이벤트를 보내고 백엔드가 뭘 기대하는지를 먼저 맞췄습니다. 문제가 생기면 누구 잘못인지보다 서로 다르게 이해한 부분이 어디인지부터 보는 편입니다.”

## 16-7. 팀원과 의견이 다르면 어떻게 하나요? / 갈등 해결 경험은?

**기억할 말:** `누가 맞냐보다 기준 → 작은 실험 → 결과로 결정`

“의견이 다르면 먼저 뭘 기준으로 결정할지 맞추려고 합니다. 관제에서 WebRTC/HLS를 계속 쓸지 MJPEG로 돌아갈지 고민했을 때도 기술이 더 멋진가보다 실제 프리즈나 운영 안정성을 기준으로 봤습니다. 가능하면 작은 실험으로 확인하고 그 결과로 결정하는 방식을 선호합니다.”

## 16-8. 스트레스나 장애 압박을 어떻게 다루나요?

**기억할 말:** `한꺼번에 안 고침 → 재현 → 하나씩 분리`

“장애가 나면 빨리 고치려고 한꺼번에 건드릴수록 더 꼬이더라고요. 그래서 먼저 재현하고 어디까지 영향을 받는지 본 다음 가설을 하나씩 확인합니다. 압박이 클수록 작업을 더 작게 나누는 게 저한테는 가장 잘 맞았습니다.”

## 16-9. 실패하거나 후회한 선택이 있나요?

**기억할 말:** `좋아 보이는 기술 고집 → 실제 실패 → 프로젝트 목적에 맞춰 철회`

“관제 프로젝트에서 WebRTC/HLS가 더 좋은 구조처럼 보여서 안정화에 시간을 많이 쓴 게 아쉽습니다. 실제로는 프리즈가 반복됐고 우리가 필요한 건 최신 기술이 아니라 안정적인 관제 화면이었습니다. 결국 MJPEG로 돌아갔고, 그 뒤로는 선택하기 전에 성공 기준이랑 언제 포기할지도 같이 정하려고 합니다.”

## 16-10. 가장 자신 있는 프로젝트는 무엇인가요?

**기억할 말:** `JK → 실행보다 권한/상태가 어려움 → 직접 깨뜨리고 고침`

“가장 자신 있는 건 JK입니다. LLM에게 실제 작업을 시키려고 만든 건데, 만들수록 모델보다 권한이나 승인, 중복 실행 같은 문제가 더 어렵다는 걸 느꼈습니다. 실제로 성공한 명령이 다시 실행되는 문제까지 겪고 기존 job 결과를 재사용하는 구조로 고쳤습니다. LLM 자동화를 실제 운영에 붙이면 어떤 문제가 생기는지를 제일 많이 배운 프로젝트라 자신 있습니다.”

두 번째 프로젝트를 묻는다면 LLM Wiki를 말하고, **“JK가 실행 자동화라면 LLM Wiki는 지식 자동화에서 검색 근거와 평가를 다룬 프로젝트”**라고 대비한다.

## 16-11. 본인을 한 문장으로 표현한다면?

**기술 면접이면:** “AI를 실제 업무에 붙였을 때 생기는 실패를 구조적으로 해결하는 개발자입니다.”

**조금 편하게 말하면:** “문제를 그냥 덮기보다 왜 생겼는지 찾고, 다음에는 같은 문제가 덜 생기게 바꾸는 사람입니다.”

## 16-12. 왜 개발자가 되고 싶었나요?

**기억할 말:** `기술 자체보다 문제 해결 → AI 모델에서 시스템으로 관심 확장`

“새 기술을 공부하는 것 자체보다 실제로 불편한 문제를 반복 가능한 방식으로 바꿀 때 더 재미를 느꼈습니다. 처음엔 의료영상 AI처럼 모델 중심이었는데 관제 시스템을 만들면서 관심이 전체 서비스로 넓어졌고, JK나 LLM Wiki를 만들면서 사람이 반복하던 일을 코드와 AI로 바꾸는 쪽이 더 잘 맞는다고 느꼈습니다.”

## 16-13. 3년 뒤 어떤 개발자가 되고 싶나요?

**기억할 말:** `특정 API 전문가 X → 현업 듣기 → 자동화 설계/운영까지`

“3년 뒤에는 특정 LLM API만 잘 쓰는 사람보다 현업이 어떻게 일하는지 듣고 자동화 구조를 설계해서 운영까지 맡을 수 있는 개발자가 되고 싶습니다. RAG나 agent도 목적이 아니라 필요한 문제에 쓰는 도구로 보고 싶습니다.”

## 16-14. 마지막으로 하고 싶은 말이 있나요?

**기억할 말:** `연차 과장 안 함 → 대신 실제 문제 경험 → 작은 업무 하나부터 증명`

“실무 연차가 긴 지원자는 아니지만 LLM 자동화를 직접 만들고 운영하면서 권한이나 검색, 중복 실행처럼 데모 이후에 생기는 문제는 꽤 겪어봤습니다. 기회가 주어진다면 처음부터 큰 플랫폼을 만들겠다고 하기보다 현업이 가장 불편해하는 업무 하나를 제대로 줄여서 결과로 보여드리고 싶습니다.”

## 16-15. HR 답변에서 계속 유지할 캐릭터

- 모르는 것을 아는 척하지 않는다.
- 연차 부족을 숨기지 않고 **직접 판단하고 운영한 범위**로 승부한다.
- 실패는 “극복했다”로 끝내지 않고 **판단 기준이 어떻게 바뀌었는지** 말한다.
- 강점과 약점을 같은 캐릭터로 연결한다: **깊게 원인을 찾되, 종료 조건으로 속도를 관리한다.**
- 모든 답변의 마지막은 가능하면 이 직무에서의 행동으로 닫는다.
- 답이 막히면 외운 문장을 찾지 말고 **“제가 실제로 겪은 예를 들면…”**으로 돌아간다.

# 17. 면접 직전 반드시 외울 것 12개

1. 현재 공고명은 **[바이브 코딩] LLM 사내 자동화 개발자**다.
2. 실제 JD 핵심은 **프롬프트 설계·관리·개선 + 워크플로 오케스트레이션 + LLM eval + 텍스트 구조화 + 부서 반복업무 자동화**다.
3. 우대 기술에는 **RAG/eval, Claude·GPT API, 로컬 LLM, Python/JavaScript, Slack·Notion·Google Workspace 연동**이 포함된다.
4. 뷰스컴퍼니는 **콘텐츠 IP·크리에이터·팬덤·커머스·글로벌 유통**을 연결하는 사업 방향을 공개적으로 강조한다.
5. 회사는 실제 유튜브 데이터를 연구에 활용하고 트렌드 리포트를 발행하는 등 데이터 활용 사례가 있다.
6. 공개 채용 선호 신호는 **빠른 실행·스스로 문제 정의·끝까지 책임·새 AI 도구 실험**이며 조직문화 전체라고 일반화하지 않는다.
7. 지원동기·왜 나인가 질문은 **필살기 → 회사 문제 → 경험 연결 → 캐릭터 한 줄**로 답한다.
8. 내 필살기는 **JK의 실행/권한/상태 분리 → LLM Wiki의 RAG/eval/근거 검색 → 스마트 안전 관제의 이벤트 분리** 세 축이다.
9. Structured Output은 **형식 보장이지 사실 보장 자체가 아니다**. eval·규칙·근거 검증을 별도로 둔다.
10. LLM 자동화의 핵심을 **prompt + workflow + state + guardrail + eval + integration**으로 설명한다.
11. “모든 걸 LLM으로”가 아니라 deterministic code와 제한적 LLM/agent를 분리한다.
12. **코딩테스트/기술면접 여부는 미확인**이며, 역질문은 “가장 먼저 자동화할 업무와 3개월 성공 기준”을 묻는다.
