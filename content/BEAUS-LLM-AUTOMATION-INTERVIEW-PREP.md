# 뷰스컴퍼니 LLM 사내 자동화 개발자 면접 완전 대비

> 목표: 회사와 JD를 외우는 자료가 아니라, **왜 이 회사가 LLM 자동화 개발자를 뽑는지 추론하고 내 프로젝트 경험을 실제 업무 문제 해결 방식으로 연결해 말하기 위한 실전 면접 노트**다.

## 먼저 결론

이 포지션은 이름만 보면 AI 모델 연구직처럼 보이지만, 공개 공고의 직무 태그와 회사 성격을 함께 보면 핵심은 **LLM을 이용해 사내 반복 업무를 빠르게 제품화·자동화하는 실무 개발자**에 가깝다.

공개 채용 정보에서 확인되는 기술 태그는 **백엔드/서버개발, 앱개발, 웹개발, 유지보수, 프론트엔드, AI, Python, JavaScript, TypeScript**다. 따라서 면접에서도 “LLM을 얼마나 깊게 학습시켰는가”만 보기보다, **사내 업무를 파악하고 API·데이터·웹 UI·자동화·운영까지 엮어 실제로 돌아가는 도구를 만들 수 있는가**를 볼 가능성이 높다.

그리고 뷰스컴퍼니 채용팀이 공개한 면접 분석에서 가장 중요한 힌트는 두 가지다.

1. **스스로 고민하고 선택해 본 사람**을 높게 평가한다.
2. 면접용으로 꾸며낸 답보다 **솔직한 선택 이유와 근거**를 높게 평가한다.

대표 역시 채용 메시지에서 경력 그 자체보다 **빠른 실행, 살아남은 경험, 끝까지 책임지는 태도**를 강조했다.

따라서 이 면접의 기본 답변 형식은 두 층으로 가져간다.

기술 경험을 깊게 설명할 때는:

**문제 → 내가 직접 고민한 선택지 → 선택 기준 → 구현 → 실패/한계 → 검증 결과 → 다시 한다면 무엇을 바꿀지**

지원동기·자기소개·“왜 당신을 뽑아야 하나요?”처럼 짧게 임팩트를 줘야 할 때는:

**① 내 필살기(증거) → ② 이 회사의 문제 → ③ 내 경험과의 연결 → ④ 문제 해결 캐릭터 한 줄**

이 두 번째 구조의 핵심은 “저는 무엇을 잘합니다”가 아니라 **그 강점이 왜 하필 이 회사의 현재 문제에 필요한지**까지 닫는 것이다.

# 2. 회사가 지금 어떤 문제를 풀고 있는가

## 2-1. 광고대행사에서 콘텐츠/IP/커머스 구조로 이동 중

뷰스컴퍼니는 뷰티 콘텐츠 중심 마케팅 대행사로 시작했지만, 최근 대표 메시지에서는 단순 광고 대행을 넘어 **크리에이터 IP → 콘텐츠 → 팬덤 → 브랜드 → 커머스/글로벌 유통**을 연결하는 구조를 강조한다.

대표 공개 자료 기준으로 2024년 매출은 136억 원, 신규 MCN 브랜드 비라운드는 첫해 56억 원 실적을 기록했다고 밝혔다. 2025년 상반기에는 매출 92.4억 원, 영업이익 12.7억 원을 공개했고 글로벌·커머스 전환을 강조했다.

이 말은 개발 포지션이 단순 사내 챗봇 하나를 만드는 역할에 머물 가능성이 낮다는 뜻이다. **마케터·콘텐츠팀·크리에이터 운영팀이 반복적으로 처리하는 리서치, 보고서, 데이터 정리, 콘텐츠 운영, 캠페인 관리 흐름을 자동화할 여지**가 크다.

## 2-2. 데이터 기반 의사결정 성향

뷰스컴퍼니는 고려대학교 연구팀과 실제 운영 중인 뷰티 유튜브 채널 데이터를 활용한 연구를 진행했고, 대표는 50개 채널과 장기간 패널 데이터, 수천 편의 쇼츠 데이터를 분석해 단순 조회수보다 재방문 시청자의 시청시간 등 구조적인 지표를 강조했다.

또 회사는 매월 올리브영·다이소 트렌드 리포트를 발행한다.

### 면접에서 연결할 포인트

“LLM을 붙이면 무엇이든 좋아진다”가 아니라,

- 어떤 원천 데이터가 있는가?
- 사람이 지금 어떤 판단을 반복하고 있는가?
- LLM이 잘하는 부분과 규칙/SQL/Python이 잘하는 부분은 무엇인가?
- 결과가 틀렸을 때 어떤 피해가 생기는가?
- 어디에 사람 승인(Human-in-the-loop)을 남길 것인가?

를 먼저 보는 태도가 잘 맞는다.

## 2-3. 2026년 시점에서 보이는 성장 단계

공개 기업 DB(나이스디앤비 제공 정보가 노출된 인크루트) 기준 2025년 매출은 **166억 4,924만 원**, 순이익은 **10억 8,544만 원**으로 표시된다. 2024년 매출 136억 7,731만 원보다 성장한 수치다. 회사가 직접 공개한 2025년 상반기 자료에서도 매출 92.4억 원, 영업이익 12.7억 원을 밝혔고, 당시 핵심 방향을 **IP 기반 글로벌 커머스**로 설명했다.

이 숫자를 면접에서 과하게 외우는 것보다 중요한 해석은 다음이다.

- 작은 실험 단계의 회사가 아니라 **이미 돈을 버는 기존 사업 위에서 새 구조를 확장하는 단계**다.
- 광고 캠페인만 수행하는 조직보다 **콘텐츠 제작 → 크리에이터 운영 → 성과 데이터 → 커머스 전환 → 글로벌 유통**으로 업무 연결점이 많아지고 있다.
- 연결점이 많아질수록 사람이 복붙하고 확인하는 운영 비용도 같이 커질 가능성이 높다.
- 따라서 LLM 사내 자동화 개발자의 가치는 “멋진 챗봇”보다 **조직이 커져도 반복 업무와 정보 흐름이 같이 복잡해지지 않도록 운영 레버리지를 만드는 것**에 있다.

## 2-4. 다른 회사와 무엇이 다른가

면접에서 “다른 회사도 AI 자동화 많이 하는데 왜 뷰스인가요?”라는 질문에 대비해 비교축을 정리한다. 아래는 공개 사업 구조를 바탕으로 한 **비교 해석**이며, 특정 경쟁사를 깎아내리는 표현은 쓰지 않는다.

### 전통 광고대행사와의 차이

전통적 대행 모델은 캠페인 수주 → 제작/집행 → 결과 보고가 중심이기 쉽다. 뷰스컴퍼니는 공개 자료에서 **브랜드와 크리에이터를 함께 키우는 구조**, 콘텐츠 반복 제작, 팬덤, 커머스 전환까지 이어지는 흐름을 강조한다.

즉 자동화 대상도 단순 보고서 작성만이 아니라 **크리에이터/콘텐츠/브랜드/성과 데이터가 이어지는 내부 운영 흐름 전체**가 될 수 있다는 점이 흥미롭다.

### 일반 MCN과의 차이

일반적인 MCN을 “크리에이터 관리·광고 매칭”으로만 보면, 비라운드는 공개 자료상 **콘텐츠를 반복 생산하고 팬덤을 형성해 커머스로 연결하는 구조** 자체를 성장 동력으로 삼고 있다. 2024년 기사에서는 비라운드가 전체 실적의 40% 이상을 차지한 핵심 성장 동력으로 소개됐다.

면접에서의 포인트는 “MCN이라 재미있어서”가 아니라 **콘텐츠 운영이 반복 가능한 시스템이 될수록 데이터와 자동화가 사업 성과에 직접 연결될 수 있다**는 점이다.

### AI 제품회사와의 차이

AI SaaS 회사라면 AI 자체가 상품일 수 있다. 이 포지션은 공개 공고명부터 **‘LLM 사내 자동화’**다. 즉 모델 성능을 판매하는 것보다, 이미 존재하는 마케팅·콘텐츠·커머스 조직 안에서 **업무 시간을 줄이고 오류를 줄이며 의사결정 속도를 높이는 AI**가 더 중요할 가능성이 높다.

이 지점이 내가 만든 JK와 특히 잘 맞는다. 나는 “AI가 답을 잘하는가”보다 **AI가 실제 도구를 실행할 때 권한·상태·중복·실패 복구를 어떻게 다룰지**를 더 오래 고민해봤다.

## 2-5. 이 회사에서 자동화 ROI가 크게 날 것 같은 이유

공개 자료만 보고 가정하면 자동화 후보는 다음 네 종류로 나뉜다.

1. **리서치형**: 올리브영/다이소/소셜 트렌드 수집, 경쟁사·제품 변화 정리
2. **운영형**: 크리에이터/캠페인 상태 업데이트, 반복 입력, 파일/시트 정리
3. **분석형**: 캠페인 KPI 집계, 성과 비교, 이상치 탐지, 리포트 초안
4. **지식형**: 과거 캠페인·제안서·가이드·브랜드 이력 검색

이 네 가지는 모두 “LLM만 붙이면 되는 일”이 아니다. API/크롤링/DB/권한/스케줄러/검증 UI와 LLM이 함께 필요하다. 그래서 웹·백엔드·AI·자동화를 전부 건드려본 경험이 차별점이 될 수 있다.

# 3. 이 포지션에서 실제로 기대할 가능성이 높은 업무

아래는 **공개 JD 전체가 아니라 회사 구조 + 기술 태그 + 포지션명 기반 추론**이다.

## 우선순위 A: 반복 사무 업무 자동화

예상 업무 예시:

- 엑셀/스프레드시트 정리와 요약
- 캠페인 성과 자료 자동 집계
- 보고서 초안 생성
- 회의록 → 액션 아이템 변환
- 메일/메신저/폼 입력 → 사내 DB나 시트 업데이트
- 브랜드/크리에이터 데이터 수집 후 정형화
- 반복 리서치 자동화

## 우선순위 A: LLM + 기존 시스템 연동

- OpenAI/Claude/Gemini 등 LLM API
- Structured Output/JSON Schema
- Tool calling / Function calling
- 사내 DB, Sheets, Drive, Slack/메일, 외부 SaaS API 연결
- Python/Node/TypeScript 기반 서버
- 간단한 React/Web UI
- 인증, 권한, 로그, 재시도

## 우선순위 A: 빠른 프로토타이핑 후 운영화

“바이브 코딩” 채용 문구상 가장 중요할 수 있다.

단순 데모를 만드는 능력보다 다음 전환이 중요하다.

**아이디어 → 1일 MVP → 현업 사용 → 실패 로그 수집 → 예외 처리 → 권한/비용/관측성 추가 → 운영 도구화**

## 우선순위 B: RAG/사내 지식검색

회사 내부에는 캠페인 리포트, 제안서, 크리에이터/브랜드 정보, 과거 성과, 업무 가이드가 누적될 가능성이 높다.

따라서 다음 질문이 나올 수 있다.

- “사내 문서를 챗봇으로 찾게 한다면 어떻게 만들 건가요?”
- “RAG와 그냥 긴 프롬프트의 차이는?”
- “검색 결과가 없을 때 어떻게 하나요?”
- “민감 문서 권한은 어떻게 막나요?”

## 우선순위 B: 웹 크롤링/리서치 자동화

마케팅 회사 특성상 트렌드와 채널 정보를 수집할 일이 많다.

여기서 중요한 건 “크롤링 할 줄 압니다”가 아니라:

- 공식 API 우선
- robots/약관/개인정보 고려
- rate limit
- 변경 감지
- 중복 제거
- 스키마 정규화
- 실패 시 재시도와 partial result
- 출처/수집시각 저장

까지 말하는 것이다.

# 4. 내 프로젝트 중 무엇을 앞세울지

## 1순위: JK

이 직무와 가장 잘 맞는다.

### 왜 강한가

JK는 단순 챗봇이 아니라 **LLM/에이전트가 실제 도구를 안전하게 실행하는 자동화 하네스**에 가깝다.

말할 핵심:

- 자연어 요청을 실제 작업으로 연결
- 프로젝트별 도구/권한 분리
- 승인 필요한 작업은 Human-in-the-loop
- `pending → approved → running → succeeded/failed` 상태 관리
- 승인 이후 같은 작업이 중복 실행되지 않도록 job resume/idempotency 고민

## 4-1. 면접 답변을 관통할 ‘필살기 → 회사 문제 → 연결 → 캐릭터’ 구조

인스타식 표현을 그대로 베끼지 말고, 내 실제 경험에 맞게 사용한다.

### 공식

1. **내 필살기:** 기술 이름이 아니라 해결한 문제를 말한다.
2. **이 회사의 문제:** 공개 자료를 근거로 이 회사에서 왜 같은 문제가 중요할지 설명한다.
3. **그래서 내가:** 내 경험이 입사 후 어떤 업무에 전이될 수 있는지 말한다.
4. **한 줄 더:** 반복되는 나의 문제 해결 습관을 남긴다.

### 나쁜 예

“저는 RAG, MCP, MQTT, React, Python을 해봤고 새로운 기술을 빨리 배웁니다.”

기술 목록은 많지만 회사가 왜 나를 뽑아야 하는지가 없다.

### 좋은 예

“LLM이 실제 작업을 실행할 때 요청과 실행을 바로 붙이지 않고 권한·승인·job 상태를 분리해, 실패하거나 결과가 끊겨도 같은 작업이 중복 실행되지 않게 만든 경험이 있습니다. 뷰스컴퍼니처럼 여러 팀의 반복 업무와 외부 도구를 연결해 자동화하려면 한 연동의 실패가 전체 업무 흐름으로 번지지 않게 만드는 게 중요하다고 봤습니다. 저는 이미 그 실패를 직접 겪고 복구 구조까지 만들어봤기 때문에, 데모가 아니라 실제 현업에서 계속 쓰는 자동화를 만드는 데 기여할 수 있다고 생각합니다. **저는 보이는 오류를 바로 덮기보다 실패가 어느 경계에서 생기는지 먼저 분리하는 편입니다.**”

## 4-2. 내 필살기 1 — ‘LLM을 실행 가능한 업무로 바꾸되, 사고가 번지지 않게 분리한다’

### ① 내 필살기

JK에서 자연어 요청과 실제 실행 사이에 **도구 레이어, 프로젝트 권한, 승인, job 상태, 결과 resume**를 분리했다. 특히 승인 후 실제 job은 성공했는데 응답이 끊기면 같은 명령이 다시 실행되는 문제를 겪으며 idempotency와 resume이 왜 필요한지 직접 배웠다.

### ② 이 회사의 문제

사내 자동화가 늘면 Sheets/Docs/DB/메일/외부 API/LLM처럼 여러 연동이 붙는다. 이때 API 하나가 느리거나 응답이 유실됐다고 전체 업무를 다시 실행하면 **중복 발송, 중복 입력, 비용 증가, 데이터 오염**이 생길 수 있다.

### ③ 그래서 내가

“자동화가 된다”보다 **어디까지 자동으로 실행하고, 어디서 승인받고, 실패했을 때 어디서부터 재개할지**를 설계해본 경험을 가져갈 수 있다.

### ④ 한 줄 더

**“저는 정상 경로보다 실패했을 때 어디까지 영향이 번지는지를 먼저 봅니다.”**

## 4-3. 내 필살기 2 — ‘LLM 답변보다 근거를 먼저 관리한다’

### ① 내 필살기

LLM Wiki에서 문서가 늘어날수록 “모델이 똑똑하면 찾겠지”가 통하지 않아, Markdown 구조 기반 chunking, lexical/vector 검색, 검색 평가, fallback을 직접 다뤘다. 실제로 자연어 검색이 특정 말투에서 0건이 되는 문제도 재현 질의와 테스트를 추가해 검색 guard를 수정했다.

### ② 이 회사의 문제

뷰스컴퍼니는 콘텐츠/캠페인/크리에이터/브랜드 데이터가 쌓이고, 데이터 기반 연구와 트렌드 리포트도 공개적으로 진행한다. 이 환경에서 AI가 그럴듯하게 틀린 과거 사례를 가져오면 현업 신뢰를 빠르게 잃는다.

### ③ 그래서 내가

사내 지식검색을 만들 때 “챗봇부터”가 아니라 **source freshness, retrieval 품질, 근거 링크, 검색 실패 시 abstention**부터 설계할 수 있다.

### ④ 한 줄 더

**“답이 이상하면 프롬프트를 먼저 만지기보다, 모델이 어떤 근거를 보고 답했는지부터 확인합니다.”**

## 4-4. 내 필살기 3 — ‘실시간 이벤트를 느슨하게 연결해봤다’

### ① 내 필살기

스마트 안전 관제에서 AI 탐지 → MQTT 이벤트 → Spring Backend → React 관제 화면으로 역할을 분리했다. 모델 추론과 알림/저장/UI를 한 프로세스에 묶지 않고 이벤트 경계로 나눴다.

### ② 이 회사의 문제

마케팅·콘텐츠 자동화도 외부 플랫폼 API, 크롤러, 분석기, LLM, 리포트 발행이 한 번에 연결될 수 있다. 한 단계가 실패했다고 이미 수집한 데이터나 앞 단계까지 버릴 필요는 없다.

### ③ 그래서 내가

Kafka 실무 경험을 과장하지 않는다. 대신 **producer/consumer 분리, 비동기 이벤트, retry, idempotency, 상태 추적**이라는 설계 문제를 다른 메시징 시스템에서 직접 다뤘고, Kafka가 필요해지면 그 개념을 빠르게 전이할 수 있다고 말한다.

### ④ 한 줄 더

**“도구 이름보다 시스템 경계를 왜 나눴는지를 설명할 수 있는 개발자이고 싶습니다.”**

## 4-5. 결국 ‘왜 나를 뽑아야 하는가’

경력 연차로만 경쟁하면 더 오래 일한 지원자가 당연히 많다. 따라서 답을 “제가 더 뛰어납니다”로 만들지 않는다. **이 포지션이 지금 필요로 할 가능성이 높은 문제를 이미 여러 각도에서 풀어봤다**고 말한다.

### 30초 답변

“저보다 실무 연차가 긴 지원자는 분명 많을 거라고 생각합니다. 대신 저는 이번 포지션에서 필요한 문제를 꽤 직접적으로 만들어보고 깨뜨려봤습니다. JK에서는 LLM이 실제 작업을 할 때 권한과 job 상태, 중복 실행을 다뤘고, LLM Wiki에서는 사내 문서를 근거 있게 찾는 RAG와 검색 평가를 만들었습니다. 또 실시간 관제에서는 이벤트 기반으로 시스템을 분리해 운영했습니다. 그래서 저는 AI 기능 하나를 만드는 사람보다 **현업 업무를 듣고, 자동화할 경계를 정하고, 실패해도 운영되는 흐름까지 끝까지 만드는 사람**으로 기여할 수 있다고 생각합니다.”

### 10초 압축

**“LLM을 써본 사람이 아니라, LLM을 실제 업무에 붙였을 때 생기는 권한·검색·중복·실패 문제를 이미 겪어본 사람이라는 점이 제 차별점입니다.”**

### 남길 캐릭터 한 줄 후보

- **문제를 바로 해결하기보다, 먼저 진짜 실패 지점을 찾는 데 자신이 있습니다.**
- **기능이 안 되면 코드를 더 붙이기보다, 어느 경계의 책임인지부터 나눕니다.**
- **빠르게 만들되, 실제로 쓰기 시작하는 순간부터는 실패 복구와 검증을 제품의 일부로 봅니다.**
- **AI가 만든 결과도 운영 환경에서는 그냥 하나의 외부 입력이라고 생각합니다.**

# 5. 가장 나올 가능성이 높은 핵심 면접 질문

## Q1. 왜 뷰스컴퍼니에 지원했나요?

### 답변 방향

“AI 회사라서”가 아니다.

**마케팅/콘텐츠 회사가 실제 데이터를 많이 갖고 있고, 반복 업무가 많아 자동화의 ROI를 바로 측정할 수 있다는 점**을 강조한다.

### 40초 답변 예시 — 4단 구조

“저는 LLM이 실제 일을 하게 만들 때 **권한·상태·근거·실패 복구를 분리해서 운영 가능한 흐름으로 만드는 경험**을 해왔습니다. 뷰스컴퍼니는 단순 광고대행보다 크리에이터 IP, 콘텐츠, 커머스, 글로벌 유통으로 사업 연결점이 늘고 있고, 공개적으로 데이터 기반 콘텐츠 연구와 트렌드 리포트도 운영하고 있습니다. 사업이 커질수록 이런 연결 사이의 반복 업무와 정보 이동을 자동화하는 게 중요해질 거라고 봤습니다. 제가 JK와 LLM Wiki에서 이미 비슷한 문제를 직접 겪고 해결해봤기 때문에, **AI 데모가 아니라 현업에서 계속 쓰는 자동화**를 만드는 데 기여할 수 있다고 판단해 지원했습니다. 저는 보이는 오류보다 진짜 실패 지점을 먼저 찾는 편입니다.”

## Q2. 왜 LLM 사내 자동화 직무인가요?

“LLM을 쓰면 개발이 빨라져서”로 끝내지 않는다.

핵심은 **반복 업무를 구조화하고 사람의 판단이 필요한 구간만 남기는 것**이다.

### 30초 답변 예시

“제가 재미를 느끼는 지점은 LLM 모델 자체보다, 사람이 반복하던 일을 분석해서 어디는 코드로 고정하고 어디만 LLM에 맡길지 정하는 과정입니다. JK를 만들면서도 자연어 요청을 바로 실행시키는 것보다 권한과 상태를 분리하는 일이 훨씬 중요했습니다. 저는 사내 자동화를 ‘AI를 많이 쓰는 일’보다 **사람의 판단이 필요한 구간만 남기고 나머지 흐름을 안전하게 줄이는 일**이라고 생각합니다.”

## Q3. 바이브 코딩을 어떻게 생각하나요?

좋은 답:

“초기 구현 속도를 크게 올릴 수 있지만, production code의 책임까지 모델에게 넘기는 방식은 아니라고 봅니다. 요구사항 쪼개기, diff 검토, 테스트, 권한, secret, 배포 검증은 사람이 책임져야 합니다.”

꼬리질문:

- AI가 만든 코드를 어떻게 검증하나요?
- 모르는 코드도 merge하나요?
- 빠른 개발과 기술부채 사이에서 기준은?

## Q4. LLM 자동화 프로젝트 하나를 처음부터 설명해 주세요.

JK를 메인으로 답한다.

**상황:** 자연어로 코딩/운영 작업을 시키고 싶었다.

**문제:** LLM이 shell을 바로 실행하면 위험하고, 승인 후 결과가 끊기면 중복 실행 문제가 생긴다.

**판단:** tool layer와 job state를 분리한다.

**구현:** 프로젝트/권한/승인/작업 상태/검증 단계.

**문제 재발:** 승인 이후 job은 성공했는데 채팅이 결과를 못 받으면 같은 명령을 또 실행.

**개선:** approvalId/jobId 기반 resume, 동일 작업 중복 방지.

**배운 점:** 자동화의 핵심은 프롬프트보다 상태 관리와 failure semantics.

## Q5. LLM API가 틀린 답을 내면 어떻게 하나요?

답변 프레임:

1. 자유 텍스트를 바로 실행하지 않는다.
2. Structured Output/JSON Schema 사용.
3. 입력 validation.
4. retrieval source 제한.
5. 위험 작업은 human approval.
6. 실행 전 dry-run/preview.
7. 결과 후 verification.
8. 실패 로그와 eval dataset 누적.

## Q6. RAG가 뭔가요? Fine-tuning과 차이는?

### 짧은 답

RAG는 질의 시점에 외부 지식을 검색해 context로 주는 방식이고, fine-tuning은 모델 파라미터가 특정 패턴/행동을 더 잘 따르게 학습하는 방식이다.

사내 최신 문서처럼 자주 바뀌고 출처가 중요한 지식은 RAG가 우선이다.

## Q7. RAG에서 검색이 잘 안 되면 어떻게 개선하나요?

- 문서 전처리
- chunk size/overlap
- heading-aware chunk
- metadata filter
- BM25 + vector hybrid
- reranking
- query rewrite
- top-k 조정
- golden query 평가
- Hit@K/MRR
- 검색 실패 시 억지 답변 금지

LLM Wiki 경험으로 연결한다.

## Q8. Prompt injection은 어떻게 막나요?

- 외부 문서를 instruction이 아니라 data로 취급
- system/developer rule과 retrieved content 분리
- allowlisted tools
- tool argument validation
- URL/파일 접근 권한 제한
- 민감 작업 approval
- secret을 context에 직접 노출하지 않기
- 출력값을 신뢰하지 말고 실행 직전 validation

## Q9. 사내 데이터 보안은 어떻게 할 건가요?

- 데이터 등급 분류
- 최소권한
- 사용자별 document ACL
- API key vault/env
- PII redaction
- audit log
- 외부 LLM 전송 여부 분리
- retention 정책
- 사내 전용 모델/로컬 모델이 필요한 정보 정의

## Q10. 자동화가 같은 작업을 두 번 실행하면 어떻게 하나요?

JK의 가장 강한 답변 포인트.

- idempotency key
- jobId
- 상태머신
- request deduplication
- retry와 re-execute 구분
- 외부 side effect 전에 상태 확인
- 완료 결과 cache/resume

## Q11. LLM 호출이 느리거나 실패하면?

- timeout
- bounded retry + exponential backoff
- retryable/non-retryable error 구분
- fallback model
- partial result
- queue
- async job
- circuit breaker 개념
- 사용자에게 진행 상태 표시

## Q12. 비용이 너무 많이 나오면?

- 작은 모델 우선 라우팅
- 필요할 때만 큰 모델
- prompt/context 압축
- RAG top-k 제한
- caching
- batch
- deterministic preprocessing은 Python으로 처리
- token/use-case별 cost metric

## Q13. 어떤 업무는 LLM을 쓰면 안 되나요?

좋은 답:

“정해진 규칙으로 100% 처리 가능한 계산, 데이터 변환, 필터링은 LLM보다 일반 코드가 낫습니다. LLM은 애매한 자연어 이해, 분류, 요약, 초안 작성처럼 확률적 판단에 사용하고, 돈/삭제/발송 같은 side effect는 규칙과 승인으로 감쌉니다.”

## Q14. Python과 TypeScript 중 무엇을 쓰겠나요?

- 웹 앱/Node API/프론트와 타입 공유: TypeScript 장점
- 팀과 기존 시스템이 기준

## Q16. 마케팅팀의 주간 리포트 작성을 자동화한다면?

중요:

- 숫자는 LLM이 계산하지 않게 한다.

- 각 문장에 source/evidence를 붙인다.
- 승인 전 자동 발송하지 않는다.

## Q21. 다른 마케팅 회사가 아니라 왜 뷰스컴퍼니인가요?

- 단순 캠페인 대행보다 **브랜드 + 크리에이터 + 콘텐츠 + 팬덤 + 커머스**를 하나의 구조로 만들려는 방향
- 비라운드라는 자체 성장축
- 데이터/알고리즘 연구와 트렌드 리포트처럼 실제 데이터 활용
- 내부 자동화가 단순 경비 절감이 아니라 **성장하는 운영 구조의 레버리지**가 될 가능성

### 답변 예시

“마케팅 회사라는 이유만으로 지원한 건 아닙니다. 뷰스컴퍼니는 공개 자료에서 브랜드와 크리에이터를 따로 보지 않고 콘텐츠를 반복 생산해 팬덤과 커머스로 연결하는 구조를 강조하고 있고, 실제로 비라운드가 큰 성장축이 됐습니다. 또 고려대와 실제 콘텐츠 데이터를 연구하고 트렌드 리포트를 운영하는 걸 보면서 데이터가 단순 보고용이 아니라 사업 구조 안에 있다는 인상을 받았습니다. 이런 회사에서는 사내 자동화가 단순한 업무 편의 기능보다 **콘텐츠와 데이터가 더 빠르게 흐르게 만드는 핵심 도구**가 될 수 있다고 생각했습니다.”

## Q22. 더 경력 많은 지원자 대신 왜 본인을 뽑아야 하나요?

### 답변 예시

“연차 자체로는 제가 유리하다고 생각하지 않습니다. 대신 이번 역할에서 생길 문제를 상당히 직접적으로 겪어봤습니다. LLM 실행 하네스를 만들며 권한과 중복 실행을 다뤘고, 사내 문서형 RAG에서는 검색 품질과 근거를 평가했고, 실시간 시스템에서는 이벤트 경계를 나눴습니다. 그리고 이걸 전부 배포하고 장애를 다시 고치는 과정까지 경험했습니다. 그래서 요구사항이 완성돼서 내려오기를 기다리기보다 **현업의 반복 업무를 직접 보고 문제를 구조화한 뒤, 작은 MVP부터 운영 가능한 수준까지 끌고 가는 역할**에 강점이 있습니다.”

## Q23. 뷰스컴퍼니에서 LLM 자동화가 실패한다면 가장 흔한 이유는 뭐라고 보나요?

### 답변 예시

“첫 번째는 자동화할 업무 자체를 잘못 고르는 것, 두 번째는 입력 데이터와 권한이 정리되지 않은 것, 세 번째는 사람이 어디서 검수해야 하는지 정하지 않은 것이라고 봅니다. 모델 정확도 문제도 있지만 실제 사내 도구는 현업이 안 쓰면 실패입니다. 그래서 저는 먼저 현재 업무를 관찰하고, deterministic code로 처리할 부분과 LLM 판단이 필요한 부분을 나눈 뒤, 수정률·시간 절감·실패율 같은 지표로 계속 볼 것 같습니다.”

# 6. 회사 맞춤 시스템 디자인: ‘뷰티 트렌드 리포트 자동화’

이건 “제가 입사하면 무조건 이걸 만들겠습니다”가 아니라 **회사 공개 활동에서 착안한 면접용 사고실험**이다.

## 문제 가정

마케터가 매월 올리브영/다이소/소셜 채널을 조사해 신제품·프로모션·카테고리 변화를 정리하고 리포트를 만든다.

## 나쁜 자동화

`웹 전체 크롤링 → 모든 HTML을 LLM에 넣음 → 보고서 자동 생성 → 바로 발행`

문제:

- 비용 큼
- 출처 불명확
- 숫자 오류
- 중복
- 사이트 변경에 취약
- 법/약관 이슈
- hallucination

## 더 나은 구조

### 1. Source Registry

수집 대상, 공식 API 여부, URL, 수집 주기, 약관/robots 메모를 관리한다.

### 2. Ingestion

API 또는 허용 범위 내 수집기로 raw data를 가져온다.

### 3. Normalization

제품명, 브랜드, 카테고리, 가격, 프로모션, 날짜, source URL을 정형 스키마로 만든다.

### 4. Deterministic Analysis

신제품 수, 가격 변화, 카테고리별 빈도 같은 수치는 SQL/Python으로 계산한다.

### 5. LLM Layer

LLM은 다음에만 사용한다.

- 비슷한 프로모션 묶기
- 변화 요약
- 카테고리 설명 초안
- 제목 후보

### 6. Evidence

각 문장/표에 source URL과 수집 시각을 남긴다.

### 7. Human Review

외부 공개 전 마케터가 변경점을 확인하고 승인한다.

### 8. Evaluation

- 리포트 작성 시간 감소
- 수정 문장 비율
- source mismatch 비율
- hallucination 건수
- 수집 실패율
- 1회 리포트당 비용

### 면접에서 한 줄

“LLM에게 리포트를 쓰게 하는 게 목표가 아니라, 사람이 6시간 하던 수집·정리·초안 작업을 1시간 검수 작업으로 바꾸는 게 목표입니다.”

# 7. LLM/자동화 CS 압축 정리

## LLM

### Temperature

출력 다양성을 조절한다. 업무 자동화/정형 출력은 일반적으로 낮은 temperature가 유리하다.

### Context Window

한 번의 요청에 넣을 수 있는 token 범위. 크다고 모든 문서를 넣는 것이 좋은 건 아니다. 관련 문서만 retrieval하는 편이 비용·정확성에 유리할 수 있다.

### Structured Output

자유 텍스트 대신 schema에 맞는 JSON을 요구한다. 후속 코드가 안정적으로 파싱하기 좋다.

### Tool Calling

LLM이 직접 DB/메일을 만지는 것이 아니라, 사용할 도구와 인자를 선택하고 애플리케이션이 검증 후 실행하는 구조다.

## RAG

### Embedding

텍스트 의미를 vector로 표현한다.

### Cosine Similarity

두 vector 방향이 얼마나 비슷한지 보는 지표.

### BM25

키워드 기반 relevance 검색. 제품명/고유명사/정확한 기술어에 강한 경우가 있다.

### Hybrid Search

Vector + lexical 검색을 결합한다.

### Reranker

1차 검색 후보를 더 비싼 모델로 다시 정렬한다.

## Backend/Automation

### Idempotency

같은 요청이 반복되어도 side effect가 한 번만 일어나도록 설계하는 성질.

### Retry

실패 원인이 일시적인 경우 다시 시도. 모든 오류를 retry하면 안 된다.

### Exponential Backoff

재시도 간격을 점점 늘려 서버/외부 API에 과부하를 주지 않는다.

### Queue

느린 작업을 요청-response와 분리해 비동기로 처리한다.

### Webhook

외부 시스템의 이벤트가 발생했을 때 우리 서버 URL로 callback을 받는 방식.

### Rate Limit

단위 시간당 요청 수를 제한한다.

### Circuit Breaker

외부 서비스가 계속 실패할 때 호출을 잠시 차단해 연쇄 장애를 막는 패턴.

### Observability

log, metric, trace로 “무엇이 실패했고 어디서 느린지” 추적 가능하게 만드는 것.

# 9. 인성/경험 질문: 뷰스컴퍼니 스타일로 준비

스마트 안전 관제 팀장 경험 또는 JK 운영.

# 16. HR·인성 면접 완성 답안

기술 질문과 달리 인성 질문은 길게 설명할수록 좋아지지 않는다. 기본 형식은 **결론 1문장 → 실제 근거 1개 → 보완 방식/직무 연결 1문장**으로 잡고, 대부분 30~60초 안에 끝낸다.

## 16-1. 30초 자기소개

“안녕하세요. 저는 **AI를 실제 업무에 붙였을 때 생기는 실패를 구조적으로 해결하는 개발자** 안진경입니다. JK에서는 LLM이 작업을 실행할 때 권한·승인·job 상태와 중복 실행 문제를 다뤘고, LLM Wiki에서는 근거 검색과 RAG 품질을 개선했습니다. 스마트 안전 관제에서는 AI 이벤트를 MQTT로 분리해 백엔드와 관제 화면까지 연결했습니다. 빠르게 만드는 것에서 끝내지 않고 **실제로 쓰일 때 어디서 실패하고 어떻게 복구할지까지 보는 점**이 제 강점입니다.”

## 16-2. 1분 자기소개

“안녕하세요. 저는 **모델 자체보다 AI가 실제 업무에서 안전하게 일하게 만드는 과정**에 강점이 있는 개발자 안진경입니다. 스마트 안전 관제 프로젝트에서는 AI 탐지부터 MQTT, Spring Backend, React 관제까지 이어지는 실시간 흐름을 만들며 시스템 경계를 나누는 경험을 했습니다. 이후 JK를 만들며 LLM이 실제 도구를 실행할 때 권한, 승인, job 상태, 중복 실행과 실패 복구가 중요하다는 걸 직접 겪었습니다. LLM Wiki에서는 문서가 많아질수록 답변보다 검색 근거가 중요하다고 판단해 RAG와 검색 평가를 만들고 자연어 검색 실패도 재현 테스트로 수정했습니다. 저는 새로운 AI 기능을 보여주는 데서 끝내기보다 **현업의 반복 업무를 보고 자동화할 경계를 정한 뒤 검증과 운영까지 책임지는 개발자**로 일하고 싶습니다.”

## 16-3. 본인의 강점은 무엇인가요? — 3개만 고정

### 강점 1. 보이는 오류보다 진짜 원인을 먼저 찾는다

“문제가 생기면 바로 코드를 더 붙이기보다 재현 조건과 실패 지점을 먼저 찾는 편입니다. LLM Wiki에서 `mqtt 왜썼지` 같은 검색이 0건이 되던 문제도 단순 동의어 부족이 아니라 검색 coverage guard가 대화체 어미까지 필수 키워드로 취급하던 문제를 찾아 수정했습니다. 그래서 **증상보다 원인을 분리해 보는 것**이 첫 번째 강점입니다.”

### 강점 2. 실패가 다른 영역으로 번지지 않게 경계를 나눈다

“스마트 안전 관제에서는 모델 추론과 알림·저장·UI를 MQTT 이벤트로 분리했고, JK에서도 요청과 실제 실행 사이에 권한·승인·job 상태를 나눴습니다. 기능 하나가 실패해도 전체 흐름을 다시 실행하지 않도록 만드는 관점이 있습니다. 여러 API와 도구를 연결하는 사내 자동화에서 특히 도움이 될 수 있다고 생각합니다.”

### 강점 3. 운영 증거가 나올 때까지 끝낸다

“개인 프로젝트도 로컬에서 되는 것으로 끝내지 않고 테스트, build, 배포, 실제 도메인에서 새 번들이 서빙되는지까지 확인합니다. 그래서 **제가 만들었다는 말보다 실제로 돌아간다는 증거를 남기는 편**입니다.”

### 10초 압축

**“제 강점은 원인을 끝까지 찾고, 실패 경계를 나누고, 실제 운영에서 확인될 때까지 마무리하는 것입니다.”**

## 16-4. 본인의 약점은 무엇인가요?

### 약점 1. 흥미로운 문제는 범위를 넓히는 경향이 있다

“문제를 발견하면 주변 구조까지 같이 개선하고 싶어져 처음 계획보다 범위가 커질 때가 있습니다. 개인 프로젝트에서 특히 그 경향을 확인했습니다. 지금은 시작 전에 **이번 작업의 종료 조건과 Must/Should를 먼저 적고, 추가 아이디어는 별도 backlog로 빼는 방식**으로 관리합니다. 빠른 실험이 중요한 환경에서는 완성도를 높이는 것만큼 어디서 끊을지 정하는 것도 중요하다고 배웠습니다.”

### 약점 2. 확신이 부족하면 검증을 오래 하는 편이다

“기술 선택에서 틀리는 걸 줄이려다 비교와 검증을 오래 할 때가 있습니다. 스마트 안전 관제의 영상 전송 방식도 여러 선택지를 오래 실험했습니다. 지금은 **되돌릴 수 있는 선택은 작은 실험으로 빨리 결정하고, 되돌리기 어려운 선택에만 깊게 검증하는 기준**을 두고 있습니다.”

피해야 할 답은 “완벽주의라 너무 열심히 한다”, “책임감이 너무 강하다”처럼 약점을 장점으로 위장하는 표현이다.

## 16-5. 성격의 장단점은?

“장점은 문제가 생겼을 때 감으로 넘기지 않고 **원인을 확인할 때까지 파고드는 편**이라는 점입니다. 반대로 그 과정에서 범위를 넓힐 수 있다는 단점이 있습니다. 그래서 최근에는 종료 조건과 검증 기준을 먼저 정하고, 지금 고칠 문제와 다음에 개선할 문제를 분리합니다.”

## 16-6. 협업할 때 어떤 스타일인가요?

“제가 맡은 부분만 잘 만드는 것보다 **팀 사이 계약을 먼저 맞추는 편**입니다. 스마트 안전 관제에서는 AI가 어떤 이벤트를 어떤 필드로 보내고 백엔드가 어떻게 소비할지를 MQTT 스키마로 맞추는 게 중요했습니다. 구현 전에 입력·출력·예외 상황을 공유하고, 문제가 생기면 사람의 잘못보다 어느 인터페이스의 가정이 달랐는지부터 봅니다.”

## 16-7. 팀원과 의견이 다르면 어떻게 하나요? / 갈등 해결 경험은?

대인 갈등을 꾸며내지 않고 **기술 판단이 달랐던 상황에서 기준을 합의한 경험**으로 답한다.

“스마트 안전 관제에서 영상 전송 방식을 고를 때 WebRTC/HLS를 계속 가져갈지, 운영 안정성이 확인된 MJPEG로 돌아갈지 고민이 있었습니다. 저는 기술 이름보다 실제 환경에서 발생한 프리즈와 인코더 종료, 목표 FPS와 운영 요구를 기준으로 비교했습니다. 결국 발표와 운영 시점에는 안정성을 우선해 MJPEG로 복귀했습니다. 의견이 다르면 ‘누가 맞는가’보다 **우리가 최적화해야 할 기준이 무엇인지 먼저 합의하고, 가능하면 작은 실험으로 판단하는 방식**을 선호합니다.”

## 16-8. 스트레스나 장애 압박을 어떻게 다루나요?

“장애가 나면 한꺼번에 고치려고 할수록 더 흔들려서 **재현 → 영향 범위 → 가설 분리 → 가장 작은 수정 → 실제 환경 검증** 순서로 대응합니다. 배포 문제에서도 로컬 build, 배포 job, 운영 도메인 반영을 따로 확인합니다. 압박이 클수록 작업을 더 작게 나누는 방식이 저한테 가장 잘 맞았습니다.”

## 16-9. 실패하거나 후회한 선택이 있나요?

“스마트 안전 관제에서 WebRTC/HLS가 구조적으로 더 좋아 보인다는 이유로 안정화에 시간을 많이 쓴 것이 기억에 남습니다. 실제 환경에서는 NVENC 종료와 프리즈가 반복됐고, 프로젝트 목적은 최신 스트리밍 기술이 아니라 **관제 화면을 안정적으로 보여주는 것**이었습니다. 결국 MJPEG로 복귀했습니다. 이후 기술 선택에서는 현재 성공 기준과 철회 기준을 먼저 정하려고 합니다.”

## 16-10. 가장 자신 있는 프로젝트는 무엇인가요?

“가장 자신 있는 프로젝트는 JK입니다. LLM에게 코딩이나 운영 작업을 맡기고 싶어 시작했는데, 만들수록 핵심 문제가 모델 성능보다 **권한·승인·실행 상태·중복 실행·결과 복구**라는 걸 알게 됐습니다. 실제로 승인 뒤 job은 성공했는데 결과가 대화로 돌아오지 않아 같은 명령이 다시 실행되는 문제를 겪었고, 기존 job 결과를 재사용하는 방향으로 구조를 개선했습니다. 기능 수보다 **LLM 자동화를 운영에 붙이면 어떤 문제가 생기는지 직접 깨뜨리고 고쳐본 경험**이 가장 많이 들어 있어 자신 있습니다.”

두 번째 프로젝트를 묻는다면 LLM Wiki를 말하고, **“JK가 실행 자동화라면 LLM Wiki는 지식 자동화에서 검색 근거와 평가를 다룬 프로젝트”**라고 대비한다.

## 16-11. 본인을 한 문장으로 표현한다면?

**“AI를 실제 업무에 붙였을 때 생기는 실패를 구조적으로 해결하고, 운영 증거가 나올 때까지 끝내는 개발자입니다.”**

조금 덜 기술적으로는 **“문제를 빨리 덮기보다 진짜 원인을 찾고, 다시 같은 문제가 나지 않게 구조를 바꾸는 사람입니다.”**

## 16-12. 왜 개발자가 되고 싶었나요?

“새로운 기술 자체를 공부할 때보다 **애매한 현실 문제를 반복 가능한 시스템으로 바꿀 때** 가장 재미를 느꼈습니다. 의료영상 AI에서는 모델 성능을 다뤘고, 스마트 안전 관제에서는 모델 결과가 실제 서비스까지 흐르게 만들며 관심이 시스템 전체로 넓어졌습니다. 이후 JK와 LLM Wiki를 만들면서 사람이 반복하던 판단과 작업을 코드와 AI로 구조화하는 데 더 큰 흥미를 느꼈습니다.”

## 16-13. 3년 뒤 어떤 개발자가 되고 싶나요?

“3년 뒤에는 특정 LLM API 하나를 잘 쓰는 사람보다 **현업 업무를 듣고 자동화 구조를 설계해 실제 운영까지 맡을 수 있는 AI Application/Backend 개발자**가 되고 싶습니다. RAG, agent, workflow를 목적이 아니라 도구로 보고 데이터·권한·평가·관측성까지 포함해 팀이 믿고 쓰는 시스템을 만드는 사람이 목표입니다.”

## 16-14. 마지막으로 하고 싶은 말이 있나요?

“저는 아직 긴 실무 연차를 가진 개발자는 아니지만, LLM 자동화를 직접 만들고 운영하면서 **권한·검색·중복·실패 복구처럼 데모 이후에 생기는 문제**를 꽤 많이 겪었습니다. 기회가 주어진다면 처음부터 큰 AI 플랫폼을 만들기보다 현업이 가장 불편해하는 업무 하나를 제대로 줄이고, 실제 사용 결과로 신뢰를 쌓겠습니다.”

## 16-15. HR 답변에서 계속 유지할 캐릭터

- 모르는 것을 아는 척하지 않는다.
- 연차 부족을 숨기지 않고 **직접 판단하고 운영한 범위**로 승부한다.
- 실패는 “극복했다”로 끝내지 않고 **판단 기준이 어떻게 바뀌었는지** 말한다.
- 강점과 약점을 같은 캐릭터로 연결한다: **깊게 원인을 찾되, 종료 조건으로 속도를 관리한다.**
- 모든 답변의 마지막은 가능하면 이 직무에서의 행동으로 닫는다.

1. 뷰스컴퍼니는 단순 광고대행사보다 **콘텐츠 IP·크리에이터·팬덤·커머스·글로벌 유통 구조**로 확장 중이다.

3. 회사는 실제 유튜브 데이터를 연구에 활용하고 트렌드 리포트를 발행할 정도로 **데이터 기반 구조화**를 강조한다.
4. 현재 공고명은 **[바이브 코딩] LLM 사내 자동화 개발자**다.
5. 공개 기술 태그는 Python, JavaScript, TypeScript + 웹/백엔드/AI 전반이다.
6. 회사 공개 면접 분석의 핵심 키워드는 **고민 + 솔직함**, 대표 메시지는 **빠른 실행 + 끝까지 책임지는 태도**다.
7. 지원동기·왜 나인가 질문은 **필살기 → 회사 문제 → 경험 연결 → 캐릭터 한 줄**로 답한다.
8. 내 필살기는 **JK의 실행/권한/상태 분리 → LLM Wiki의 근거 검색 → 스마트 안전 관제의 이벤트 분리** 세 축이다.
9. “Kafka를 해봤다”처럼 과장하지 말고, MQTT에서 다룬 **producer/consumer·비동기·idempotency 개념의 전이 가능성**을 말한다.
10. LLM 자동화의 핵심을 **prompt가 아니라 workflow + tool + state + guardrail + eval**로 설명한다.
11. “모든 걸 LLM으로”가 아니라 deterministic code와 LLM을 분리한다.
12. 역질문은 “지금 가장 먼저 자동화하고 싶은 업무와 3개월 성공 기준”을 묻는다.
