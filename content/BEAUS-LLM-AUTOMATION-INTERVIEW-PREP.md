# 뷰스컴퍼니 LLM 사내 자동화 개발자 — 면접 직전 압축본

> **목표:** 많이 외우지 않는다. **결론부터 말하고, 이유와 경험을 붙인다.**
>
> **내 캐릭터:** 새로운 기술을 빠르게 배우고, 작은 결과물을 빠르게 만든 뒤 로그·테스트·실사용으로 검증하는 주니어 자동화 개발자.

---

## 0. 면접장 들어가기 전 이것만 본다

### 한 줄 자기소개

> **AI를 실제 서비스와 업무에 연결하고, 빠르게 만든 뒤 검증하며 개선하는 개발자 안진경입니다.**

### 모든 답변 공식

**결론 1문장 → 이유 1~2개 → 내 경험/회사 연결 1문장**

답이 막히면:

> **현업 흐름 확인 → 반복/병목 찾기 → 작은 MVP → 로그·테스트·사용자 확인 → 효과 측정 → 확장**

### JD를 면접용으로 기억할 3축

공고 문구를 통째로 암기하지 말고 아래 방향으로 답변을 통일한다.

1. **빠르게 만든다** — 작은 결과물을 먼저 만든다.
2. **빠르게 배운다** — 필요한 기술을 기능 단위로 익혀 바로 적용한다.
3. **실제 일을 줄인다** — LLM 자체보다 현업의 반복 업무와 병목을 줄인다.

| JD 축 | 내 경험 | 한 문장 |
| --- | --- | --- |
| 빠르게 만든다 | 개인 서비스·JK·LLM Wiki | “작게 만들고 실제 동작부터 확인합니다.” |
| 빠르게 배운다 | AI → Spring Boot → LLM/RAG/배포 | “필요한 기술을 기능 단위로 배우고 바로 적용합니다.” |
| 실제 일을 줄인다 | JK·LLM Wiki·자동화 관심 | “기술보다 사람이 반복하는 흐름부터 봅니다.” |

# 1. 뷰스컴퍼니는 3줄만 기억

- 과거 **D2C·자사몰·퍼포먼스 마케팅 경험**을 기반으로 사업을 확장해왔다.
- 현재는 **뷰티 콘텐츠·크리에이터·마케팅·커머스**를 연결하는 성격이 강하다.
- 최근에는 **글로벌 K-뷰티·북미/유럽 인플루언서·TikTok Live·AI 콘텐츠** 관련 채용도 진행하고 있다.

### 회사 설명 20초

> **“뷰스컴퍼니는 뷰티 브랜드의 성장을 콘텐츠와 크리에이터, 마케팅, 커머스로 연결하고 글로벌 영역까지 확장하는 회사라고 이해했습니다.”** 사업 채널이 많아질수록 리서치·데이터 정리·번역·보고처럼 반복되는 정보 업무도 커질 수 있어서, LLM 자동화가 실제 생산성으로 연결되기 좋은 환경이라고 생각했습니다.

**주의:** 회사 내부 프로세스를 직접 아는 것처럼 말하지 않는다. 자동화 사례는 **공개된 사업 구조를 보고 세운 가설**이라고 한다.

# 2. 1분 자기소개

> “안녕하십니까. **AI를 실제 서비스와 업무에 연결하는 개발자 안진경입니다.**
>
> 의공학을 전공하며 인공지능과 딥러닝을 공부했고, 이후 서비스 구현 역량을 넓히기 위해 SK쉴더스 지능형 애플리케이션 개발 과정에서 Spring Boot 기반 스마트 안전관제 시스템을 개발했습니다.
>
> 최근에는 LLM을 실제 개발과 업무 흐름에 연결하는 데 관심을 가지고, 기존 MCP 프로젝트를 제 개발 환경에 맞게 고도화한 JK와 문서 검색형 LLM Wiki 같은 개인 프로젝트를 진행했습니다.
>
> 저는 **새로운 기술을 빠르게 배우고 작은 결과물을 먼저 만든 뒤, 로그와 테스트로 검증하며 개선하는 개발자**입니다. 이런 방식이 이번 LLM 사내 자동화 직무와 잘 맞는다고 생각해 지원했습니다.”

### 기억 키워드

`AI → 서비스 개발 → LLM 자동화 → 빠른 학습/구현 → 검증`

문장을 통째로 외우지 않는다.

**기억:** `실제 업무 적용 → 반복 정보업무 → 내 방식과 맞음`

## Q3. 입사하면 무엇부터 자동화하고 싶나요?

**첫 문장:**
> **“기술부터 정하지 않고, 반복 빈도가 높고 효과를 측정하기 쉬운 업무부터 찾겠습니다.”**

**답변:**
> “기술부터 정하지 않고, 반복 빈도가 높고 효과를 측정하기 쉬운 업무부터 찾겠습니다. 예를 들어 크리에이터 후보 조사나 캠페인 자료 취합 같은 업무가 실제로 반복되고 있는지 현업에 먼저 확인하겠습니다. 그중 실패 위험이 낮은 하나를 작은 MVP로 만들고, 절감 시간·오류·사용률을 본 뒤 효과가 있으면 확장하겠습니다.”

**자동화 가설 하나만 기억:**

`크리에이터/캠페인 자료 수집 → 정리·분류 → 요약/보고서 초안 → 사람 검수`

**기억:** `현업 → 반복업무 → MVP → 측정 → 확장`

**기억:** `흩어진 지식 → 검색 → 근거 → 사내 지식 활용`

# 4. JK — 이 프로젝트는 이렇게 설명한다

## 20초 설명

> **“JK는 기존 로컬 MCP 실행기 프로젝트를 가져와, 제가 실제로 계속 쓸 수 있도록 승인과 클라우드 중앙 제어를 추가해 고도화한 프로젝트입니다.”** 원래는 로컬에서 AI 명령을 실행하는 형태였는데, 실제로 사용하면서 위험한 명령을 바로 실행하는 문제와 로컬에서만 쓸 수 있는 한계를 느꼈습니다. 그래서 승인 시스템과 대시보드, OCI 중앙 서버, Windows 실행기 분리 구조를 추가했습니다.

### 시작점과 내가 추가한 것

```text
기존 로컬 MCP 실행기
        ↓
승인 시스템 추가
        ↓
승인/상태 대시보드
        ↓
OCI 중앙 Control Plane
        ↓
Windows Executor 분리
        ↓
외부 MCP 도메인 연결
        ↓
실행 결과/상태/복구 흐름 고도화
```

### 왜 이렇게 바꿨나요?

> **“실제로 계속 사용하려면 실행 가능성보다 안전성과 운영성이 더 중요하다고 느꼈기 때문입니다.”** 파일 삭제나 배포처럼 영향이 큰 명령을 AI가 바로 실행하는 것은 위험했고, 로컬 MCP만으로는 PC 밖의 환경에서 쓰기 어려웠습니다. 그래서 위험 작업은 사람이 승인하고, 중앙 서버가 요청·상태를 관리하며 실제 실행은 Windows가 담당하게 역할을 나눴습니다.

### 본인이 직접 한 부분은?

> **“기반 프로젝트를 처음부터 만든 것은 아닙니다.”** 기존 프로젝트를 사용하면서 필요한 기능과 문제를 정의했고, 승인 시스템·클라우드 중앙 제어·Windows 실행기 분리·대시보드 같은 고도화 방향을 정했습니다. 구현에는 AI를 적극적으로 활용했고, 저는 요구사항·권한 경계·완료 기준을 정하고 실제 환경에서 동작을 반복 검증했습니다.

이 답은 숨기지 않는다. 오히려 **오픈소스를 이해하고 실제 문제에 맞게 확장한 경험**으로 말한다.

### TypeScript / Node.js / MCP를 쉽게 설명하면

> **“TypeScript는 JK의 도구와 요청 구조를 안전하게 정의하는 데 사용했고, Node.js는 그 로직과 API를 실제로 실행하는 런타임입니다. MCP는 AI가 JK의 기능을 정해진 형식으로 호출하는 규격이고, MCP 도메인은 외부의 ChatGPT 같은 클라이언트가 OCI의 JK에 접근하기 위한 주소입니다.”**

딱 이것만 기억:

`TypeScript = 작성/타입`  
`Node.js = 실행`  
`MCP = AI와 도구의 호출 규격`  
`MCP 도메인 = 외부 AI가 들어오는 주소`

### 현재 흐름

```text
ChatGPT / AI Client
        ↓
mcp.jingyeong.cloud
        ↓
OCI의 JK Control Plane
  요청 / 승인 / 상태 관리
        ↓
Windows Executor
  실제 명령 실행
        ↓
실행 결과 반환
```

### 면접에서 JK로 보여줄 포인트

> **“AI가 코드를 생성하는 것에서 끝나지 않고, 실제 실행 환경과 연결했을 때 생기는 권한·승인·상태 관리 문제를 직접 경험하고 개선해봤습니다.”**

이게 LLM 사내 자동화 직무와 연결되는 핵심이다.

# 5. 스마트 안전관제 — 가장 강한 정식 프로젝트

## 20초 설명

> **“AI 탐지 결과를 실제 관제 서비스까지 연결한 5인 팀 프로젝트이고, 저는 팀장과 AI 파이프라인을 담당했습니다.”** RTSP 영상에서 이상행동을 탐지하고 MQTT로 이벤트를 전달한 뒤 Spring Boot와 React 관제 화면까지 연결했습니다. 단순 모델 성능뿐 아니라 실시간 동작과 오탐, 스트리밍 문제를 함께 다뤘습니다.

### 문제 해결 경험

**결론:**
> **“문제가 생기면 같은 조건에서 재현하고 전후를 비교해서 판단하려고 했습니다.”**

Tracking ID나 프레임 동기화 문제가 생겼을 때 같은 테스트 영상으로 반복 재현하고 조건을 조정했습니다. 면접에서 수치를 말할 경우 반드시 **측정 조건과 함께** 말한다.

### 왜 이 직무와 관련 있나요?

> **“AI 모델 하나보다 여러 시스템을 연결해 실제 사용 흐름을 만드는 경험을 했다는 점이 가장 관련 있다고 생각합니다.”** LLM 자동화도 결국 모델만 호출하는 것이 아니라 API·데이터·업무 흐름·사용자까지 연결해야 한다고 생각합니다.

---

# 6. 자동화 설계 질문은 이것 하나로 통일

1. **사람이 현재 하는 순서**를 본다.
2. 입력·출력·사람의 판단 지점을 나눈다.
3. 반복 빈도·소요 시간·오류 위험을 확인한다.
4. 규칙으로 되는 것은 일반 코드/스크립트를 쓴다.
5. 비정형 텍스트의 분류·요약·작성처럼 필요한 부분에만 LLM을 쓴다.
6. 처음에는 사람 검수를 남긴 작은 MVP로 만든다.
7. **시간 절감 / 오류율 / 사용률 / 비용**을 보고 확장한다.

### 왜 Agent부터 안 쓰나요?

> **“업무에 필요한 가장 단순한 구조부터 선택하겠습니다.”** 여러 도구를 스스로 선택하고 단계별 판단이 필요한 경우 Agent가 유용하지만, 순서가 정해진 업무라면 일반 워크플로우가 더 예측 가능하고 유지보수하기 쉽다고 생각합니다.

### LLM이 필요 없는 업무라면?

> **“LLM을 쓰지 않겠습니다.”** 규칙이 명확하면 일반 코드나 기존 SaaS가 더 단순하고 안정적입니다. 자동화 개발자의 목표는 LLM 사용 자체가 아니라 **실제 일을 줄이는 것**이라고 생각합니다.

# 7. 인성 질문 — 모두 JD 3축으로 돌아온다

| 질문 | 결론 | 가져올 경험 |
| --- | --- | --- |
| 강점 | **빠르게 배우고 실제 결과물까지 만든다** | 개인 프로젝트 + JK |
| 단점 | **초기에 범위를 넓게 잡는 편이었다** | 우선순위/종료조건으로 보완 |
| 실패 | **좋은 기술보다 필요한 기술 선택이 중요했다** | 스트리밍 기술 변경 경험 |

| 새 기술 | **필요한 범위부터 배우고 기능으로 확인한다** | LLM/MCP/Cloudflare 등 |

### 단점 답변

> **“초기에 해보고 싶은 범위를 넓게 잡는 편이 있었습니다.”** 그래서 최근에는 작업 시작 전에 우선순위와 종료 조건을 먼저 정하고, 작은 기능이 실제로 동작한 뒤 다음 단계로 넘어가려고 합니다.
